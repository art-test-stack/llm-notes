Learning objectives

You should be able to trace a request through admission, prefill, decode, preemption, and cleanup; compare scheduling policies against explicit SLOs; explain the full lifecycle of a paged-KV block table; and design benchmarks, autoscaling, and recovery for a production serving fleet.

Transitions are committed by the scheduler, not inferred from kernel completion alone. For example, a prefill kernel can finish while the request remains Prefilling because more prompt chunks remain. Cancellation and failure can occur from every non-terminal state.

What happens at each scheduler iteration

  1. Ingest arrivals, cancellations, completed transfers, and worker failures; finalize completed sequences and release their references.
  2. Refresh estimates: free KV blocks, runnable tokens, deadlines, waiting age, per-tenant debt, prefix hits, and adapter residency.
  3. Protect already-streaming work by budgeting decode tokens first, subject to priority and deadline rules.
  4. Choose queued admissions only when their model/adapter and conservative KV reservation fit; attach compatible cached prefixes.
  5. Fill the remaining token budget with bounded prefill chunks, rather than allowing one long prompt to monopolize the iteration.
  6. If the batch still cannot fit, delay admission or select a documented pressure response: evict reusable cache, preempt, recompute, swap, or reject.
  7. Build model-compatible batches, allocate or restore blocks transactionally, dispatch kernels, then commit state and stream outputs only after success.

Static versus continuous batching

Static batching waits for a fixed group and runs it together. It is simple but suffers when requests have unequal lengths: completed requests leave wasted slots.

Continuous batching dynamically inserts new requests and removes completed ones between decoding iterations. It improves utilization and throughput but makes scheduling, cache ownership, and per-request state more complex.

Scheduling policies

No policy is best without an objective. The scheduler must balance TTFT, TPOT, deadlines, throughput, fairness, cache locality, and uncertain output lengths.

A practical policy is hierarchical: enforce tenant quotas, reject infeasible SLOs, prioritize due decodes, age waiters within each class, and fill leftover tokens with prefill chunks. Batch compatibility remains a hard constraint after ranking.

Detailed mixed scheduling scenario

Paged-KV allocator

Paged attention stores keys and values in fixed-size physical blocks. If a block holds B token positions, logical token t maps to logical block floor(t/B) and offset t mod B; the per-sequence block table maps that logical block to a physical block ID.

  • Block size: smaller blocks reduce waste and make eviction granular but enlarge block tables and allocator/kernel overhead. Larger blocks improve locality but waste more tail space.
  • Internal fragmentation: only the last block is normally partial. Waste is between zero and B − 1 token slots per live sequence, plus padding imposed by the kernel.
  • Refcounts: each physical block records live sequence references and reusable-cache ownership. A block returns to the free list only at refcount zero and after in-flight kernels or transfers release it.
  • Prefix sharing: exact token prefixes may reference the same immutable full blocks when model version, adapter, tokenizer/chat template, positional semantics, and relevant inference settings match.
  • Copy-on-write: a shared partial tail cannot be appended in place. Allocate a private block, copy the valid entries, update only the writer’s table, then decrement the old reference.
  • Isolation: block handles are scoped to worker, model version, and tenant policy; generation counters prevent stale IDs from resolving to reallocated memory. Kernels receive validated per-request tables, never raw cross-tenant cache keys.

Block-table lifecycle

  1. Create: on admission, create an empty table under the request identity. A prefix lookup may attach physical blocks 41 and 87, incrementing each refcount from 1 to 2.
  2. Grow: prefill needs another logical block. Reserve physical block 12 first, run the kernel, and publish L2 → P12 only after success. A failed kernel rolls back the reservation without exposing a half-written block.
  3. Fork/share: two samples can share immutable full blocks. Their block tables point to the same physical IDs and increment refcounts.
  4. Copy on write: one sample appends into a shared partial block. It copies valid KV to P19, changes only its last table entry to P19, and decrements the shared block.
  5. Preempt or swap: freeze the table at a committed token index. Recompute discards private block references; swapping serializes block contents plus model/version and position metadata, then frees device references after transfer acknowledgement.
  6. Finish: remove the request table and decrement every reference. Eligible full prefix blocks may remain under a cache-owned reference; private and ineligible blocks return to the free list.
  7. Evict: select an unpinned reusable prefix, remove its cache index entry first, wait for lookup readers, decrement its cache references, and recycle only zero-refcount blocks. Live request references remain valid.

The table is correctness- and security-critical: a valid tensor shape does not prove that a physical block belongs to the right token position, model, adapter, or tenant.

A common order is: stop admission, reclaim completed/private allocations, evict cold reusable prefixes, then choose recompute or swap for preemptible requests. Reject before risking OOM. Cost policies may differ, but no policy may expose stale, cross-request, or partially transferred KV.

Worker and cache-pressure recovery sequence

  1. A decode worker reports a high-watermark alarm and misses health probes while it owns 20 live streams and several reusable prefixes.
  2. The router marks it draining/unhealthy: no new admissions. The scheduler stops dispatch after the last acknowledged token boundary and propagates cancellations separately.
  3. Cold, zero-live-reference prefix entries are evicted first. Cache index entries are invalidated before their cache refcounts are released.
  4. For recoverable live requests, the control plane snapshots request tokens, committed output index, sampler/RNG state, block-table metadata, model/adapter version, and the last acknowledged stream sequence number.
  5. Long KV states are transferred to a compatible worker if the source remains responsive; each destination validates all blocks before publishing the new table. Short states are recomputed from tokens when that is faster.
  6. If transfer is partial or the worker dies, discard the incomplete destination table. Recompute only requests whose API contract permits a resumable retry; otherwise terminate with an explicit partial-stream failure.
  7. The router resumes at the next sequence number, suppresses duplicate tokens already acknowledged, and keeps the old worker quarantined until its leases expire. Metrics record recovery path, lost work, and SLO impact.

Prefill/decode disaggregation

Disaggregation specializes workers: prefill workers favor high compute throughput on wide prompt batches, while decode workers favor memory bandwidth, low iteration jitter, and stable streaming. A router sends the prompt to a compatible prefill pool, then hands its KV and request state to a decode pool.

  • KV transfer: move or expose KV blocks with layout, dtype, model/version, adapter, position, and integrity metadata. The destination publishes the request only when every block is ready.
  • Routing: choose pools with matching model and adapter residency, enough destination memory, predicted transfer time, and end-to-end SLO slack.
  • Queue coupling: prefill admission must account for downstream decode capacity. Otherwise prefills complete faster than decode can drain, filling transfer buffers and KV memory.
  • Fault recovery: retain tokens and a committed handoff record until decode acknowledges ownership. Retry prefill or transfer only under a request contract that prevents duplicate streamed output.

Disaggregation loses when prompts are short, outputs are short, transfer latency rivals compute, the interconnect is congested, model/adapter diversity destroys locality, traffic is too small to fill specialized pools, or separate pools strand capacity. Colocation is often better for small balanced workloads.

Multi-model and multi-adapter serving

  • Compatible batching: a kernel batch normally shares base model, weights/version, tensor layout, KV dtype, and execution path. Requests with different LoRA adapters can batch only when the runtime’s multi-adapter kernel supports it; otherwise group by adapter.
  • LoRA adapter cache: keep hot adapters in device memory and colder adapters in CPU/storage tiers. Track bytes, load latency, frequency, recency, pinning, and in-flight references rather than treating every adapter as equal.
  • Model-version routing: make the version part of the route and cache key. Sticky routing can preserve prefix and adapter locality; canaries need explicit weights and isolated metrics. Never silently continue a sequence on different weights.
  • Loading and eviction: coalesce concurrent loads for the same adapter, verify identity/checksum, then atomically publish it. Evict only adapters with no in-flight users; otherwise route elsewhere or delay admission. Reserve memory so adapter loading cannot consume the live-KV safety margin.

Benchmark methodology

Open-loop versus closed-loop load

An open-loop generator schedules arrivals independently of completions, commonly with Poisson arrivals or a replayed production trace. It exposes queue growth and overload because slow responses do not reduce offered load. A closed-loop generator sends the next request only after a client’s previous request completes; it models interactive users but self-throttles under latency and can conceal saturation. Report both offered and achieved rates.

Concrete open-loop benchmark design

  1. Build a deterministic request corpus with production-like correlations among prompt length, output limit, actual output length, model/adapter, priority, cacheable prefix, and cancellation rate. Include short chat, medium retrieval, and long-document tails; do not use one fixed length.
  2. Warm every replica through model loading, graph/kernel compilation, allocator growth, and a declared adapter/prefix-cache state. Measure both cold-start separately and steady-state after warm-up.
  3. For each offered rate, generate arrivals from a fixed-seed Poisson process for at least 10 minutes after warm-up. Timestamp arrivals at the generator before queueing and consume streams without artificial backpressure.
  4. Sweep from light load through saturation—for example 20%, 40%, 60%, 80%, 90%, 100%, 110%, and 130% of a pilot capacity—without changing prompt/output distributions between points.
  5. Record request-level TTFT, TPOT, end-to-end latency, status, deadline, tokens, queue time, prefix hit, preemptions, swaps, worker, model/adapter, and cancellation. Record allocator, queue, transfer, and GPU metrics at the same time.
  6. Plot offered request/s and token/s against achieved throughput, p50/p95/p99 TTFT and TPOT, queue depth, rejection/error rate, and goodput. Saturation is where queues/tails grow without proportional completed throughput—not merely where GPU utilization reaches 100%.

Production operation

Autoscaling

Scale from demand signals that lead user-visible latency: queued prefill tokens, active decode sequences, predicted KV bytes, deadline slack, adapter/model demand, and goodput—not GPU utilization alone. Use separate signals for prefill and decode pools. Scale out early enough to cover model and adapter load time; cap admission while new replicas warm. Scale in only after a stabilization window and drain replicas before removal.

Health checks, draining, and retries

  • Health checks: distinguish liveness from readiness. Readiness requires loaded weights, allocator headroom, responsive scheduler iterations, healthy collective/network links, and no incompatible version state.
  • Replica draining: stop new admissions, allow bounded active work to finish, migrate or recompute eligible requests, expire cache leases, and force termination only after a deadline. Keep the route registered for existing stream ownership until handoff completes.
  • Streaming retries: before the first token, a retry can be transparent if request idempotency is preserved. After tokens are visible, retry only with sequence-numbered resumability or return an explicit partial failure; a fresh blind retry can duplicate or diverge text.
  • Partial failures: treat incomplete KV transfers, one failed tensor-parallel rank, sampler failure, and broken client streams as distinct stages. Quarantine suspect resources and make the whole distributed step fail atomically.
  • Cancellation: propagate from gateway to queue, scheduler, kernels where supported, transfer tasks, and stream writer. Release blocks only after in-flight users acknowledge; measure cancellation-to-release lag.

Trace-level observability

Give each request one trace across gateway, admission, queue, tokenizer, prefix lookup, adapter/model load, every prefill chunk, decode iterations, KV allocation/swap/transfer, sampling, and streaming. Spans should carry request/tenant pseudonymous IDs, model and adapter versions, priority, state transitions, logical token counts, queue reason, worker, batch size, block counts, cache outcome, preemption/retry count, stream sequence number, and SLO slack. Do not record raw prompts, generated text, credentials, or cross-tenant cache keys by default.

Failure modes and review checklist

  • head-of-line blocking by long prefills;
  • fragmentation or block-table corruption;
  • burst admission causing OOM;
  • starvation of low-priority or long requests;
  • prefix reuse across incompatible model/adapters;
  • queueing hidden from benchmark reports;
  • peak throughput measured with unrealistic equal lengths;
  • retrying streamed requests without idempotent semantics.
  • prefill/decode queues scaled independently until completed KV has nowhere to go;
  • adapter eviction while an in-flight batch still references its weights;
  • autoscaling on utilization after queueing and goodput have already collapsed.

Peer-programming scenario

Extend the mixed scenario above to one 64k-token document and 100 short chats. Specify the arrival model, TTFT/TPOT SLOs, per-iteration token budget, chunk size, aging rule, KV block size and high-watermark action. Then explain exactly when the document moves through Prefilling, Preempted, Swapped or recomputed, and Decoding. A strong answer defines the objective and correctness boundary before choosing a policy.
