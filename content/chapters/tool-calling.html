Learning objectives

You should be able to distinguish structured generation from reliable execution, define a typed tool contract, validate and authorize arguments, handle deadlines and retries, and evaluate tool selection, argument quality, execution, and final task success separately.

The execution boundary

A language model should not directly perform external side effects. It emits a proposed action that an orchestration layer validates and executes:

user request → model proposes tool + arguments
→ schema validation → authorization/policy check
→ execution with deadline → result validation
→ model receives observation → final response or next action

The tool interface is a software contract. It should specify:

  • stable name and purpose;
  • typed arguments and required fields;
  • units, ranges, enumerations, and defaults;
  • output schema;
  • possible error classes;
  • timeout and rate-limit behavior;
  • whether the operation has side effects;
  • idempotency and authorization requirements.

Structured-generation methods

Structured generation is a spectrum. Some methods merely ask the model to follow a format; others remove invalid next tokens during decoding. The stronger methods can guarantee syntax, but none guarantees that the selected tool, values, permissions, or real-world action are correct.

Schema-to-grammar compilation

A compiler can translate each supported schema construct into grammar productions: object properties become keyed productions, required fields determine admissible object forms, arrays recurse into item productions, and unions or enums become alternatives. The decoder then:

  1. keeps the current automaton or parser state for the generated prefix;
  2. maps vocabulary tokens to the bytes or characters they would append;
  3. masks tokens whose entire expansion has no valid transition;
  4. samples from the remaining logits and advances the state;
  5. allows end-of-sequence only from an accepting state.

Compilation is not automatically complete. Unsupported regular expressions, unrestricted recursion, duplicate keys, whitespace, token fragments that span grammar terminals, and tokenizer-specific escapes need explicit semantics. Cache compiled grammars by schema version and tokenizer. Dense masking over the full vocabulary can be expensive; precomputed valid-token sets, sparse masks, and state caches trade memory for lower per-token latency. Narrow masks can also distort the model distribution: they prevent invalid surface forms but do not teach the model which valid alternative is intended.

Schema semantics

The contract must say more than “returns JSON.” A production schema should make the following cases explicit:

ConstructContract questionImplementation note
Required and optional fieldsMust the caller supply the value, may it be omitted, or may it explicitly be null?Omitted, defaulted, and null are different states. Do not silently invent a consequential missing value.
UnionsWhich alternative applies, and is there a discriminator?Prefer tagged unions such as {"kind":"email",...}; overlapping untagged shapes create validation and decoding ambiguity.
EnumsIs the value a closed machine identifier or user-facing text?Use stable identifiers. Adding an enum value can break exhaustive consumers even if parsing still succeeds.
Recursive structuresWhat depth and size are allowed?Grammar recursion needs runtime depth, node-count, and payload limits to prevent unbounded generation or parser work.
Numeric rangesAre bounds inclusive, and what precision is valid?A grammar may constrain lexical shape; validate numeric value, precision, overflow, and domain range after parsing.
UnitsIs duration milliseconds, seconds, or an ISO duration?Encode units in field names or a typed value such as {"value":5,"unit":"minutes"}; normalize only at the boundary.
Cross-field constraintsMust start < end, or must one field be present only for a given mode?These are usually semantic validation rules, not token-level grammar rules. Return a path-specific, non-secret error.
Backward-compatible schema versioningWhich producer and consumer versions interoperate?Prefer additive optional fields, stable meanings, tolerant readers, and explicit version negotiation. Rename or type-change via a new version; keep old handlers during migration.

JSON schemas, grammars, or constrained decoding can force syntactically valid output. This improves parseability, but syntax is not semantics. A valid date can be in the past, a valid user ID can refer to the wrong tenant, and a valid file path can exceed authorization.

Any syntax guarantee is mode- and provider-specific and applies only when the documented decoding mode completes successfully. Truncation, invalid or premature EOS, refusal or error paths, transport interruption, and unsupported modes can leave no complete value, so parsing and error handling remain mandatory. Grammar membership additionally assumes correct grammar compilation, incremental parser state, complete handling of tokenizer byte sequences—including tokens spanning terminals—EOS only in an accepting state, and no abort before acceptance. Even then, membership proves neither semantic correctness nor authorization; tests should cover valid completion, premature truncation, invalid EOS, and terminal-spanning tokens.

Validation therefore remains layered: parse and schema shape; ranges, units, and cross-field invariants; live resource state; tenant authorization; then user confirmation for sensitive side effects. A valid date can be in the past, and a valid user ID can name the wrong tenant.

Tool-selection and training pipeline

  1. Tool-needed decision: classify among answer directly, ask a clarification, retrieve knowledge, or call a tool. Include “no tool” examples so availability does not become a reason to call.
  2. Catalogue retrieval: for a large catalogue, retrieve a small candidate set using the request, conversation state, permissions, and tool metadata. Measure recall before blaming the ranker; a missing candidate cannot be selected later. This is a specialised retrieval problem.
  3. Tool ranking: compare candidate purpose, preconditions, side effects, cost, and freshness. Train with hard negatives: tools sharing verbs or entities but differing in scope, tenant, or side-effect semantics.
  4. Argument generation: generate only from user-provided, trusted contextual, or explicitly defaultable values; record each argument's provenance.
  5. Clarification: if a required consequential parameter is absent or ambiguous, ask a targeted question instead of guessing. Ask only for values the system cannot safely resolve.
  6. Multi-tool plan: represent dependencies between calls, run only independent read-only calls in parallel, and revalidate later steps against observations.

Ambiguous overlapping tools need more than polished descriptions. Define discriminating examples and counterexamples, canonical routing rules, and an abstain/clarify option. During supervised fine-tuning, mix tool-needed negatives, single-tool calls, missing-parameter dialogues, overlapping-tool contrasts, and multi-step trajectories. Preference or reinforcement training should reward final task success and correct abstention while penalising invalid, unnecessary, unauthorised, or duplicate calls. Avoid training only on successful oracle traces: models must also learn recovery from timeouts, stale results, and partial failure. Bounded orchestration and plan-state design are covered in Agents, Orchestration and Agent Evaluation.

Execution protocol

Keep proposal, approval, and execution as distinct states. A robust protocol is:

1. proposed call       model emits tool, arguments, schema version, and intent
2. validation          parse; check shape, units, ranges, invariants, and freshness
3. authorization       bind the authenticated principal and tenant; check this operation/resource
4. confirmation        show the consequential action and resolved values when policy requires it
5. idempotency key     orchestrator binds a stable key to principal + operation + canonical arguments
6. execution           trusted adapter calls the dependency under a deadline
7. observation         record typed status, result/error, provenance, and operation ID
8. retry/compensation  retry only eligible failures with the same key, or compensate completed steps
9. final acknowledgement report confirmed outcome, partial outcome, or unresolved state without guessing

Authorization happens immediately before execution, not once at conversation start: permissions and resource ownership can change. Confirmation is not authorization; a user may confirm an operation they are not permitted to perform. The model never supplies trusted identity, tenant, policy decisions, or secrets as ordinary arguments.

Transactional side effects

At-least-once delivery retries until acknowledged and may duplicate an operation. At-most-once delivery suppresses retries or duplicates but may lose an operation after an ambiguous failure. Exactly-once effects require cooperation from the destination—typically a durable idempotency record and atomic effect—not merely a client retry policy.

Use the same idempotency key on duplicate retries, and require the provider to return the original result for that key. A key must be scoped to the authenticated principal and canonical operation; trusting a model-invented key permits collisions or replay. For high-impact actions, use two-phase confirmation: first resolve and display the exact proposal, then execute only after fresh confirmation without allowing the model to mutate the confirmed arguments.

Example: transfer with an ambiguous timeout

propose transfer €40 from account A to merchant M
→ validate currency, positive amount, balance rule, and recipient identity
→ authorize principal for account A
→ display “Send €40.00 to M?” and receive confirmation
→ persist operation op_731 + idempotency key k_731 + canonical request
→ execute transfer(k_731) → client times out before seeing the response
→ query operation(k_731), rather than issuing a new transfer
→ if COMMITTED: acknowledge the original receipt; do not retry the effect
→ if NOT_FOUND and deadline remains: retry transfer with k_731
→ if PARTIAL: expose completed steps and run the predeclared compensating action if safe
→ report committed, compensated, partially completed, or unresolved—never infer success

Multi-tool workflows are usually sagas rather than database transactions. Predefine compensating actions such as cancelling a reservation, but recognise that compensation is a new fallible business action, not a perfect rollback. Preserve partial-success details and ask the user how to proceed when completed effects cannot be reversed.

Stateful and asynchronous tools

Long-running tools return a job handle instead of holding an LLM request open. The orchestrator, not free-form model memory, owns the job state:

submit_export(arguments, idempotency_key, deadline)
→ {job_id: "job_42", status: "queued", version: 1}
→ persist job handle, owner/tenant, creation time, and end-to-end deadline
→ poll get_job("job_42", after_version=1) with bounded backoff
→ {status: "running", progress: {completed: 63, total: 100}, version: 7}
→ user requests cancel → authorize → cancel_job("job_42")
→ poll until terminal {cancelled | succeeded | failed | timed_out}
→ on succeeded, fetch typed result and validate it before acknowledgement

Progress is advisory unless the API defines exact semantics; it must not be treated as committed output. Propagate cancellation to child work where supported and distinguish a client wait timeout from job failure—the job may still be running. Eventual consistency means a read immediately after a write can be stale. Include observation timestamps, monotonic versions or ETags, and source provenance; reject out-of-order observations and re-read authoritative state before a dependent side effect. Polling should honour provider hints, cap backoff, stop at the end-to-end deadline, and resume from a persisted handle after process restart. Event streams or webhooks can reduce polling, but still need authentication, deduplication, ordering rules, and reconciliation.

Timeouts and retries

Each call needs a deadline inside the remaining end-to-end budget and explicit error classes. Retry only transient failures, use bounded exponential backoff with jitter, respect provider rate-limit hints, and stop on validation, authorization, or confirmed application errors. Reads are usually safer to retry than writes; side-effect retries require an idempotency contract and an ambiguity-resolution query.

Security boundaries

Tool descriptions, arguments, and outputs cross trust boundaries. Apply the controls below together; prompt wording is not an authorization mechanism. See the broader threat model in LLM Security, Prompt Injection and Data Leakage.

  • Tool-output prompt injection: treat results—including retrieved documents and error strings—as untrusted data, delimit them from instructions, preserve provenance, validate their schema, and prevent them from granting tools or changing policy.
  • Argument injection: use typed adapter calls rather than shell or query concatenation; allow-list operations, canonicalise identifiers, validate paths/URLs, and keep untrusted text in data positions.
  • Secret handling: inject credentials inside the trusted adapter from a secret store. Never place secrets in model context, schemas, tool output, repair prompts, or logs; redact dependency errors.
  • Least privilege: issue short-lived, narrowly scoped credentials per tool and operation. Separate read tools from write tools and constrain network, filesystem, process, and spend capabilities.
  • Tenant authorization: derive principal and tenant from authenticated orchestration state, enforce resource-level access on every call, and include tenant in caches and idempotency scopes.
  • Sandbox boundaries: run risky interpreters, browsers, and file tools in isolated processes with explicit mounts, network egress rules, CPU/memory/time limits, and audited outputs. A sandbox limits impact; it does not make malicious output trustworthy.

Evaluation datasets and layered matrix

Build versioned datasets from hand-written contracts, anonymised production traces, incidents, and generated perturbations. Include direct-answer negatives, answerable and unanswerable requests, required-parameter omissions, paraphrases, equivalent units and timestamps, confusing catalogue neighbours, malformed outputs, permission changes, duplicate deliveries, timeouts before and after commit, partial failures, stale observations, injected tool output, and long-running jobs. Label valid alternative traces rather than one exact string, split by tool family and scenario template to limit leakage, and retain hidden adversarial and temporal holdouts. Evaluate deterministic adapters with fixed fixtures and model policy over repeated seeded trials.

End-to-end task success can hide unsafe extra actions; exact argument match can reject equally valid representations. Keep layer metrics as release gates and use the experimental guidance in LLM Evaluation and Benchmark Design.

Failure modes

  • hallucinated tool names;
  • syntactically valid but semantically wrong arguments;
  • units omitted or confused;
  • retries duplicate a side effect;
  • timeout at one layer exceeds the global deadline;
  • tool result trusted as an instruction;
  • exception details expose credentials or internal data;
  • model claims success after execution failure;
  • a large tool catalog creates routing ambiguity.
