Processes, threads, and asyncio tasks

These are three different ways to organize work. A process is a running program with its own address space. A thread is an execution path inside a process, so threads in the same process can access the same Python objects. An asyncio task is a coroutine scheduled by an event loop; it is not automatically a thread or a process.

UnitMemoryTypical executionGood first use
ProcessSeparate address space by defaultCan execute on another CPU coreHeavy pure-Python CPU work
ThreadShares objects in its processSubject to the CPython GIL for Python bytecodeBlocking synchronous I/O
Asyncio taskShares its event-loop threadRuns until it cooperatively pauses at awaitMany async-compatible I/O operations

Concurrency means several jobs make progress during the same period. Parallelism means instructions literally execute at the same instant. Several processes are concurrent and can also run in parallel on different CPU cores. Several ordinary CPython threads are concurrent, but pure Python bytecode normally does not run in parallel because of the GIL.

The CPython Global Interpreter Lock

The Global Interpreter Lock, or GIL, is a lock used by standard CPython. A thread must hold it before executing Python bytecode, so only one thread in a process normally executes Python instructions at a time.

Thread A: execute Python ── wait ───────── execute Python
Thread B: wait ─────────── execute Python ──────────────

This does not make threads useless:

  • A thread releases the CPU while it waits for many I/O operations.
  • Native Rust, C, and C++ libraries may release the GIL while doing their real work.
  • NumPy, PyTorch, tokenizers, image libraries, and compression libraries may have native or internal parallelism, depending on the operation.

The GIL also does not make application logic thread-safe. An invariant may span several Python operations, allowing another thread to run between the check and the update.

Blocking I/O and CPU-bound work

I/O is communication with something outside the CPU: a network service, database, disk, terminal, or another process. A blocking call keeps the calling thread waiting until the operation finishes.

response = socket.recv(1024)

# This cannot run until recv() returns.
process(response)

During that wait, the CPU may be mostly idle. Threads can overlap several such waits:

import time
from concurrent.futures import ThreadPoolExecutor


def fake_request(request_id: int) -> int:
    # Simulate a synchronous network call.
    time.sleep(1)
    return request_id


with ThreadPoolExecutor(max_workers=3) as executor:
    results = list(executor.map(fake_request, [1, 2, 3]))

# The three one-second waits overlap, so this takes about one second.
print(results)

A task is CPU-bound when calculations, rather than waiting, dominate its runtime. A large pure-Python loop is the standard example:

def sum_of_squares(limit: int) -> int:
    # The CPU continually executes Python operations.
    return sum(number * number for number in range(limit))

Processes can bypass the per-process GIL for this workload. Native numerical or GPU work is different: the library may already parallelize internally, so adding Python workers can oversubscribe the machine and make it slower. Benchmark the complete pipeline.

Threads share ordinary Python objects

Every thread in a process can refer to the same list, dictionary, model, or other object. This is convenient for read-only state but dangerous for shared mutation.

from threading import Thread

values: list[int] = []


def worker() -> None:
    # This is the same list object used by the main thread.
    values.append(42)


thread = Thread(target=worker)
thread.start()  # Begin running worker().
thread.join()   # Wait until that thread finishes.

print(values)  # [42]

A simple design is to let workers return values and let one owner assemble the shared result:

from concurrent.futures import ThreadPoolExecutor


def fetch(ticket_id: str) -> tuple[str, dict]:
    record = call_external_api(ticket_id)
    return ticket_id, record


with ThreadPoolExecutor(max_workers=4) as executor:
    pairs = executor.map(fetch, ["T1", "T2", "T3"])

# Only the main thread mutates this dictionary.
tickets_by_id = dict(pairs)

Processes, start methods, start, and join

Ordinary Python objects are not automatically shared between processes. A child modifying its list does not modify the parent list:

from multiprocessing import Process


def worker(values: list[int]) -> None:
    # This mutation belongs to the child process.
    values.append(42)
    print("Child:", values)  # [1, 2, 42]


if __name__ == "__main__":
    values = [1, 2]
    process = Process(target=worker, args=(values,))
    process.start()
    process.join()

    print("Parent:", values)  # [1, 2]

The main guard is important because a spawned child imports the module. Without the guard, importing it could create more children recursively.

Start methodWhat happensMain consequence
spawnStarts a fresh interpreter and reconstructs serialized argumentsImportable functions and picklable arguments are required; startup is relatively expensive
forkChild inherits the parent's memory imagePages begin copy-on-write but ordinary mutations remain private; inherited threads, locks, or CUDA state can be unsafe
forkserverA clean server process forks childrenAvoids inheriting much of the main process's complicated state

Copy-on-write is a physical-memory optimization, not ordinary shared mutable state. Parent and child may initially map the same unchanged memory pages. When either writes to a page, the operating system gives it a private copy.

To run several workers concurrently, start all of them before joining any of them:

workers = [
    Process(target=do_work, args=(worker_id,))
    for worker_id in range(4)
]

# Launch every process first.
for worker in workers:
    worker.start()

# The workers are now concurrent and can run in parallel on multiple cores.
# join() only makes the main process wait for a worker to terminate.
for worker in workers:
    worker.join()

Starting and immediately joining inside the same loop would serialize the jobs:

for worker in workers:
    worker.start()
    worker.join()  # The next worker is not started until this one ends.

Inter-process communication and shared memory

IPC means inter-process communication. Passing an ordinary Python object commonly requires serialization, byte transfer, deserialization, and synchronization. This fixed work can dominate thousands of tiny tasks.

from multiprocessing import Process, Queue


def worker(queue: Queue) -> None:
    result = {"ticket_count": 42}
    queue.put(result)  # Serialize and transfer to the parent.


if __name__ == "__main__":
    queue = Queue()
    process = Process(target=worker, args=(queue,))
    process.start()

    result = queue.get()  # Receive and reconstruct the dictionary.
    process.join()
    print(result)

Queues and pipes are communication mechanisms. multiprocessing.Value, Array, shared_memory, memory-mapped files, manager proxies, and shared CPU tensor storage provide explicit sharing. Shared mutation still needs a lock whenever workers can touch the same logical state.

import torch
import torch.multiprocessing as mp


def fill_row(tensor: torch.Tensor, row: int) -> None:
    # Each worker owns a different row, so these writes do not conflict.
    tensor[row].fill_(row + 1)


if __name__ == "__main__":
    context = mp.get_context("spawn")
    tensor = torch.zeros(4, 3)
    tensor.share_memory_()  # Share the underlying CPU storage.

    workers = [
        context.Process(target=fill_row, args=(tensor, row))
        for row in range(4)
    ]
    for worker in workers:
        worker.start()
    for worker in workers:
        worker.join()

    print(tensor)

Prefer fewer substantial jobs over many tiny IPC exchanges. Batch records before sending them to a process pool, and return compact results whenever possible.

Asyncio is cooperative concurrency

An asyncio event loop normally runs in one thread. A coroutine executes until it reaches an await whose result is not ready. It pauses, allowing the loop to run another ready task.

import asyncio


async def fake_request(request_id: int) -> int:
    print("Starting", request_id)
    await asyncio.sleep(1 / request_id)  # Pause without blocking the loop.
    print("Finished", request_id)
    return request_id


async def main() -> None:
    results = await asyncio.gather(
        fake_request(1),
        fake_request(2),
        fake_request(3),
    )
    # gather() preserves input order even if tasks finish in another order.
    print(results)  # [1, 2, 3]


if __name__ == "__main__":
    asyncio.run(main())

Calling main() by itself merely creates a coroutine object. If it is neither awaited nor passed to asyncio.run(), Python warns that the coroutine was never awaited.

A blocking function freezes the event-loop thread:

import time


async def bad_task() -> None:
    time.sleep(5)  # No other asyncio task can run on this loop meanwhile.

Use an async-compatible API, or move an unavoidable synchronous call to a thread:

async def main() -> None:
    results = await asyncio.gather(
        asyncio.to_thread(blocking_library_call, 1),
        asyncio.to_thread(blocking_library_call, 2),
    )
    print(results)

Asyncio can also coordinate a process pool for CPU work:

import asyncio
from concurrent.futures import ProcessPoolExecutor


def cpu_work(limit: int) -> int:
    # Module-level functions are importable by spawned workers.
    return sum(number * number for number in range(limit))


async def main() -> None:
    loop = asyncio.get_running_loop()

    with ProcessPoolExecutor(max_workers=2) as pool:
        jobs = [
            loop.run_in_executor(pool, cpu_work, 10_000_000),
            loop.run_in_executor(pool, cpu_work, 10_000_000),
        ]
        print(await asyncio.gather(*jobs))


if __name__ == "__main__":
    asyncio.run(main())

asyncio.create_task() creates an asyncio task, not a new OS thread or process. Threads and processes can be created inside async code, but calling blocking operations such as join() directly would freeze the event-loop thread.

PyTorch DataLoader worker semantics

DataLoader(..., num_workers=0) loads samples in the main process. A positive num_workers creates worker processes.

For a map-style dataset, the main process's sampler chooses indices and sends them to workers. Each worker calls its own dataset instance's __getitem__, and the produced samples are returned to the main process. The index assignment is coordinated, but ordinary mutable dataset state is not automatically shared.

from torch.utils.data import DataLoader, Dataset


class RecordingDataset(Dataset):
    def __init__(self) -> None:
        self.seen_indices: list[int] = []

    def __len__(self) -> int:
        return 4

    def __getitem__(self, index: int) -> int:
        # This changes only this worker's dataset state.
        self.seen_indices.append(index)
        return index


if __name__ == "__main__":
    dataset = RecordingDataset()
    loader = DataLoader(dataset, batch_size=1, num_workers=2)
    list(loader)

    print(dataset.seen_indices)  # [] in the parent process

persistent_workers=True preserves each worker's private dataset and cache between epochs. It does not merge those caches or expose them to the parent. For large read-only data, prefer file paths, memory-mapped arrays, databases designed for concurrent reads, or explicitly shared CPU tensors instead of millions of nested Python objects.

loader = DataLoader(
    dataset,
    batch_size=32,
    num_workers=4,
    multiprocessing_context="spawn",
    persistent_workers=True,
    pin_memory=True,
)

pin_memory=True prepares CPU batches for faster asynchronous transfer to a CUDA device. It does not create general shared Python memory. A common design is for workers to return CPU tensors and for the main process to transfer them:

for cpu_batch in loader:
    gpu_batch = cpu_batch.to("cuda", non_blocking=True)

Avoid initializing CUDA or returning CUDA tensors inside ordinary loader workers. Use module-level dataset classes, collators, and worker initialization functions with spawn; local functions and lambdas are often not picklable.

Choosing concurrency for tokenization

Tokenization is CPU work, but “CPU-bound” does not automatically imply “use processes.” The implementation determines whether the GIL matters.

  • A slow tokenizer implemented mainly in Python may benefit from processes over a sufficiently large corpus.
  • A fast Rust- or C++-backed tokenizer may release the GIL and may already use native threads.
  • For a few strings, worker startup and IPC cost more than they save.

For a modern fast tokenizer, begin with one batched call:

encoded = tokenizer(
    texts,                 # A list of strings, processed as a batch.
    truncation=True,
    padding=False,
    add_special_tokens=True,
)

This reduces repeated Python-to-native calls compared with [tokenizer.encode(text) for text in texts]. For a fixed large corpus, offline batched preprocessing is often simpler than repeating tokenization every epoch. If profiling still shows a CPU bottleneck, test a small number of processes and watch for tokenizer duplication, serialization overhead, memory use, and CPU oversubscription.

When tokenization must happen during loading, batching it in a collator is usually better than encoding one string at a time:

def collate_texts(texts: list[str]):
    # With num_workers > 0, this runs inside a loader worker process.
    return tokenizer(
        texts,
        padding=True,
        truncation=True,
        return_tensors="pt",
    )


loader = DataLoader(
    raw_text_dataset,
    batch_size=32,
    num_workers=4,
    collate_fn=collate_texts,
)

Iterable, iterator, and generator

An iterable can produce an iterator through iter(obj). An iterator remembers a traversal position and produces the next value through next(obj). A generator is one convenient kind of iterator.

ObjectIterableIteratorGeneratorNormally reusable
listYesNoNoYes
rangeYesNoNoYes
iter(list)YesYesNoNo
Generator objectYesYesYesNo
map, filter, zipYesYesNoNo
 
numbers = [10, 20, 30]
iterator = iter(numbers)

print(next(iterator))  # 10
print(next(iterator))  # 20

# next(numbers) would fail: a list is iterable, not an iterator.
assert iter(iterator) is iterator

Iterators are stateful and normally one-shot:

iterator = iter([10, 20])

print(list(iterator))  # [10, 20]
print(list(iterator))  # []: it is exhausted

Generator functions and expressions

A function containing yield creates a generator object when called. Its body begins only when a value is requested:

def countdown(start: int):
    current = start

    while current > 0:
        yield current  # Produce one value and pause here.
        current -= 1


generator = countdown(3)
print(next(generator))  # 3
print(next(generator))  # 2

yield from delegates to another iterable:

def combine(first, second):
    yield from first
    yield from second


print(list(combine([1, 2], [3, 4])))  # [1, 2, 3, 4]

A generator expression resembles a tuple, but the for gives it generator-expression syntax:

lazy_squares = (number * number for number in range(5))
print(type(lazy_squares))  # <class 'generator'>

grouped = (1)    # int: parentheses only group the expression
one_item = (1,)  # tuple: the comma creates the tuple

# Python has no tuple-comprehension syntax. Consume a generator explicitly.
squares_tuple = tuple(number * number for number in range(5))

The corresponding eager comprehensions use brackets or braces:

[number**2 for number in range(5)]          # list
{number**2 for number in range(5)}          # set
{number: number**2 for number in range(5)}  # dict
(number**2 for number in range(5))          # generator

Eager versus lazy, reusable versus one-shot

These are two independent questions. Eager or lazy asks when values are computed. Reusable or one-shot asks whether traversal can start again.

def square(number: int) -> int:
    print("Computing", number)
    return number * number


eager = [square(number) for number in range(3)]
# All three calls have already happened.

lazy = (square(number) for number in range(3))
# No call has happened yet.

first = next(lazy)  # Only square(0) runs now.

A list is eager and reusable. A generator is lazy and one-shot. A range is compact and reusable: it stores boundaries rather than materializing every Python integer. Laziness saves memory and supports streams, but exceptions and side effects also happen later, during consumption.

References, identity, shallow copies, and deep copies

Python assignment binds a name to an object; it does not copy the object. is asks whether two names identify the same object, while == asks whether their values compare equal.

original = {"tags": ["urgent"]}
alias = original

assert alias is original
alias["tags"].append("customer")

print(original)  # {"tags": ["urgent", "customer"]}

A shallow copy creates a new outer container but reuses nested objects:

original = {"owner": "alice", "tags": ["urgent"]}
shallow = original.copy()

assert shallow is not original
assert shallow["tags"] is original["tags"]

shallow["owner"] = "bob"          # Only shallow changes here.
shallow["tags"].append("customer")  # The nested list is shared.

A deep copy recursively constructs independent nested objects where possible:

import copy

original = {"tags": ["urgent"]}
deep = copy.deepcopy(original)

assert deep["tags"] is not original["tags"]
deep["tags"].append("customer")

print(original["tags"])  # ["urgent"]

Deep copies can be expensive and can duplicate more state than intended. Prefer clear ownership and immutable data when that avoids copying altogether.

Mutable and immutable objects

A mutable object can change in place. Lists, dictionaries, sets, byte arrays, tensors, and most class instances are mutable. Integers, floats, booleans, strings, bytes, tuples, frozensets, and None are immutable.

numbers = [1, 2]
alias = numbers
numbers.append(3)
print(alias)  # [1, 2, 3]: the shared list changed

text = "hello"
old_text = text
text += " world"  # Build a new string and rebind text.
print(old_text)    # hello

An immutable tuple can contain a mutable object. The tuple's references cannot be replaced, but the referenced object can still change:

value = ([1, 2],)
value[0].append(3)
print(value)  # ([1, 2, 3],)

Mutable default arguments are shared across calls because defaults are evaluated once, when the function is defined:

def add_bad(value: int, values: list[int] = []) -> list[int]:
    values.append(value)
    return values


print(add_bad(1))  # [1]
print(add_bad(2))  # [1, 2]

Create a fresh object inside the function instead:

def add_good(
    value: int,
    values: list[int] | None = None,
) -> list[int]:
    if values is None:
        values = []

    values.append(value)
    return values

EAFP and LBYL error handling

LBYL, “look before you leap,” checks a condition first. EAFP, “easier to ask forgiveness than permission,” attempts the operation and catches the specific expected failure.

# LBYL
if ticket_id in tickets:
    ticket = tickets[ticket_id]
else:
    ticket = None

# EAFP
try:
    ticket = tickets[ticket_id]
except KeyError:
    ticket = None

EAFP is especially useful when the operation itself is the only reliable test. A separate existence check can race with another process:

from pathlib import Path


def read_configuration(path: Path) -> str | None:
    try:
        return path.read_text()
    except FileNotFoundError:
        return None

Catch the narrow failure whose meaning is understood. except Exception could hide permission problems, encoding errors, or programming bugs.

Context managers and guaranteed cleanup

A context manager owns setup and cleanup around a block. A file is closed when the block exits, whether it succeeds, raises, or returns:

with open("tickets.json", "r") as file:
    content = file.read()

# file.close() has run here.

The structure is approximately a try/finally:

file = open("tickets.json", "r")
try:
    content = file.read()
finally:
    file.close()

Custom context managers make ownership explicit:

from contextlib import contextmanager


@contextmanager
def managed_connection(connect):
    connection = connect()
    try:
        yield connection  # Give the resource to the with block.
    finally:
        connection.close()


with managed_connection(create_connection) as connection:
    connection.send("hello")

Locks are context managers too. with lock: acquires the lock before the block and releases it afterward, including when an exception occurs.

Closures, scope, and late binding

Python resolves a name through local, enclosing, global, and built-in scopes, often abbreviated LEGB. A closure is a nested function that retains access to names from an enclosing function:

def make_multiplier(factor: int):
    def multiply(value: int) -> int:
        return value * factor

    return multiply


double = make_multiplier(2)
print(double(10))  # 20

Closures normally look up the enclosed variable when called, producing the late-binding surprise:

functions = []

for number in range(3):
    functions.append(lambda: number)

print([function() for function in functions])  # [2, 2, 2]

Capture the current value through a default argument evaluated during function creation:

functions = []

for number in range(3):
    functions.append(lambda number=number: number)

print([function() for function in functions])  # [0, 1, 2]

Use nonlocal to rebind a name from an enclosing function and global to rebind a module-level name:

def make_counter():
    count = 0

    def increment() -> int:
        nonlocal count
        count += 1
        return count

    return increment

Race conditions, locks, and atomicity

A race condition occurs when correctness depends on how concurrent operations are interleaved. Suppose two threads both try to withdraw 80 from a balance of 100. Both can pass the check before either performs the subtraction.

import time
from threading import Thread

balance = 100


def unsafe_withdraw(amount: int) -> None:
    global balance

    if balance >= amount:
        time.sleep(0.01)  # Make the harmful interleaving easier to observe.
        balance -= amount

The invariant is that the balance must never become negative. The complete check-and-update sequence is the critical section, so protect the entire sequence with one lock:

from threading import Lock

balance = 100
balance_lock = Lock()


def withdraw(amount: int) -> bool:
    global balance

    with balance_lock:
        if balance < amount:
            return False

        balance -= amount
        return True

The block is atomic relative to code using the same lock: another such worker cannot observe it halfway through. A lock should protect an invariant, not merely one line that happens to write. Reducing shared mutable state is usually even simpler than adding more locks.

Measure end-to-end throughput and latency rather than assuming more workers are faster. Account for startup, serialization, IPC, memory duplication, native thread pools, ordering, cancellation, and cleanup. The clearest design usually assigns ownership explicitly: workers compute or fetch results, while one component owns each mutable piece of state.
