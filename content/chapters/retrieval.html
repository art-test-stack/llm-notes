Learning objectives

You should be able to distinguish sparse retrieval, dense bi-encoders, cross-encoders, late interaction, and hybrid systems; explain how embedding models are trained; select indexing and ranking metrics; and diagnose retrieval independently from generation.

Technical framing

The RAG landmark combines parametric generation with an external corpus or index, commonly called non-parametric memory; the retriever, reranker, encoders, and generator may still be parameterized. REALM integrates latent retrieval during pretraining. In its reported setup, RETRO retrieved from a roughly two-trillion-token corpus and let a smaller model reach Pile performance comparable to named much larger baselines. That result is not a general law that retrieval replaces parameter scaling. These systems shift some knowledge from weights into an updatable corpus, but introduce indexing, recall, context-construction, and latency concerns; retrieval alone guarantees neither factuality nor freshness, grounding, or attribution.

Cross-attention provides the conditioning mechanism:

Q = X_query W_Q K = X_context W_K V = X_context W_V Attention(Q,K,V) = softmax(QKᵀ / √d) V

Queries and context may have different sequence lengths. In latent cross-attention, a small set of latent queries reads a much larger input. This reduces later computation but creates a bottleneck that may discard information.

Retrieval architecture

Candidate generation and candidate scoring are separate stages:

  • BM25 / sparse retrieval: strong for exact terminology, identifiers, rare words, and lexical constraints.
  • Dense bi-encoder: embeds query and document independently, enabling approximate nearest-neighbour search and semantic matching.
  • Hybrid retrieval: combines sparse and dense scores or candidate sets.
  • Cross-encoder reranker: jointly encodes query and candidate for stronger relevance estimates at higher latency.
  • Late interaction: retains multiple token-level vectors, trading storage for finer-grained matching.

Cosine similarity equals a dot product only after vector normalization. Index configuration, embedding version, and score calibration must therefore be recorded together.

Metadata filters—tenant, permission, date, geography, document type—are security and correctness constraints. They should be applied in retrieval, not left to the language model after unauthorized text has entered context.

BM25 from first principles

BM25 scores a document D against query q by adding a contribution for each query term. A common positive-IDF form is:

score(q,D) = Σ[t ∈ q] IDF(t) · f(t,D)(k₁ + 1) ───────────────────────────── f(t,D) + k₁(1 - b + b|D|/avgdl) IDF(t) = ln(1 + (N - n(t) + 0.5)/(n(t) + 0.5))

Here f(t,D) is term frequency in the document, |D| is document length, avgdl is average document length, N is the corpus size, and n(t) is the number of documents containing the term. The IDF term makes rare terms more valuable. BM25 usually omits query-term frequency because web-style queries are short; variants can add it.

The fraction is a saturating term-frequency function: the first few matches help most, while repeated occurrences approach an upper bound of k₁ + 1. k₁ controls how quickly frequency saturates: k₁ = 0 makes term presence almost binary, while a larger value rewards repetition for longer. b controls document-length normalization: b = 0 applies none, while b = 1 fully scales by |D|/avgdl. Typical starting points are k₁ ≈ 1.2 and b ≈ 0.75, but both should be tuned on the target corpus.

Worked retrieval example

Suppose N = 1,000,000, avgdl = 100, k₁ = 1.2, and b = 0.75. The query is vector database. A 150-token document contains vector three times and database once; their document frequencies are 1,000 and 10,000.

length term = k₁(1 - b + b|D|/avgdl) = 1.2(0.25 + 0.75·1.5) = 1.65 IDF(vector) ≈ ln(1 + 999000.5/1000.5) = 6.907 IDF(database) ≈ ln(1 + 990000.5/10000.5) = 4.605 TFsat(vector) = 3·2.2/(3 + 1.65) = 1.419 TFsat(database) = 1·2.2/(1 + 1.65) = 0.830 score ≈ 6.907·1.419 + 4.605·0.830 = 13.62

The rarer term contributes more, three occurrences do not count as three independent matches, and the above-average document length reduces both contributions. Scores are meaningful for ranking within one index and query, not as calibrated probabilities.

Training dense retrievers

A bi-encoder computes q = Eq(text) and d = Ed(passage) independently. Dot product and cosine similarity differ unless vectors are normalized:

dot(q,d) = qᵀd cos(q,d) = qᵀd / (||q||₂ ||d||₂) q̂ = q/||q||₂, d̂ = d/||d||₂ ⇒ cos(q,d) = q̂ᵀd̂

Unnormalized dot product lets vector norms affect rank and can encode confidence or popularity, but it may encourage norm growth. L2 normalization removes that degree of freedom and makes cosine search implementable as maximum inner-product search. Apply the same normalization during training, indexing, and serving.

An InfoNCE-style loss gives one positive passage probability mass over a candidate pool:

s(q,d) = sim(Eq(q), Ed(d)) Lq = -log [ exp(s(q,d⁺)/τ) / Σ[d ∈ {d⁺} ∪ Nq] exp(s(q,d)/τ) ]

The temperature τ controls softmax sharpness: lower values amplify small score differences and gradients, while values that are too low make noisy or false negatives dominate. It can be fixed or learned, but must be monitored with embedding norms and negative-pool size.

Queries and documents are asymmetric: a query states an information need, while a passage contains evidence and is often much longer. Encoders may share weights for efficiency or use separate weights, prompts, and maximum lengths to model that asymmetry. Pooling can use a special [CLS] token, masked mean pooling, or the final non-padding token. Mean pooling spreads evidence across tokens; special-token or last-token pooling delegates aggregation to training. The deployed pooling, truncation, and tokenization must exactly match index construction.

Training data should match deployment query style, document domain, language, and granularity. A retriever trained on short factual questions may perform poorly on long engineering requests or code identifiers. Domain adaptation should therefore be evaluated against both target-domain recall and regression on broader traffic.

A false negative is actually relevant but labelled negative. It pushes useful evidence away and is especially likely for duplicate passages, multi-answer questions, and in-batch pools. Mitigate it with deduplication, multiple-positive labels, teacher or human checks, and a margin that ignores ambiguous candidates rather than forcing every pair apart.

Distributed training can all-gather passage embeddings across workers, turning a local batch of B into roughly world_size × B in-batch candidates. This improves pool diversity but increases communication and the chance of false negatives; gradients and masking semantics must be explicit. A practical curriculum starts with random and in-batch negatives, introduces BM25 hard negatives after basic alignment, then periodically mines dense or cross-encoder negatives from fresh checkpoints. Re-mine between rounds rather than on every step, and retain a mix of easy and hard examples so training does not collapse onto a narrow error distribution.

Late interaction

A ColBERT-style model encodes every query and document token into contextual, usually normalized vectors. It performs the expensive encoding independently, then retains token-level interaction at search time:

Eq(q) = [q₁, …, qₘ] Ed(D) = [d₁, …, dₙ] MaxSim(qᵢ,D) = max[j=1…n] qᵢᵀdⱼ score(q,D) = Σ[i=1…m] MaxSim(qᵢ,D)

Each query token finds its best document-token match, preserving fine-grained evidence that a single pooled vector can blur. The price is storing and searching many vectors per passage rather than one; compression and token pruning help, but memory, index traffic, and latency remain above a bi-encoder.

Indexing and approximate search

Flat exact search computes similarity against every vector and provides the recall ceiling for a given embedding model. Approximate-nearest-neighbour indexes reduce the number or cost of comparisons, trading some index recall for latency and memory.

IndexInternal ideaConstruction parametersQuery parametersBest fit and trade-offs
Flat exactContiguous vectors; exhaustive SIMD/GPU scanVector dtype and layoutBatch size; optional exact top-kHighest recall, trivial updates, no training; latency and bandwidth grow linearly with corpus size
HNSWMulti-layer proximity graph; greedy descent then local beam searchM neighbours per node; efConstructionefSearchExcellent recall/latency and incremental inserts; graph overhead costs memory and heavy deletion is awkward
IVFK-means coarse centroids partition vectors into inverted listsnlist, training sample, clustering iterationsnprobe lists searchedScales well and batches efficiently; misses vectors when the right cell is not probed
IVF/PQIVF pruning plus product-quantized residual or vector codesnlist, PQ subspaces m, bits per code, codebooksnprobe, candidates to rescoreLowest memory and fast distance tables; quantization adds ranking error and requires representative training data

Product quantization splits a vector into m subvectors and replaces each with a short codebook identifier. Distances are approximated by table lookups, often followed by exact rescoring of a small candidate set. More HNSW efSearch, IVF nprobe, or rescore candidates generally improves recall while increasing latency. Larger M/efConstruction, more IVF centroids, and larger PQ codebooks increase build cost or memory but can improve the attainable frontier. Tune construction and query parameters separately against exact-search neighbours.

The index version must be coupled to the embedding model, normalization, pooling, tokenization, distance function, and document preprocessing. Re-embedding only part of a corpus with a new model creates an incoherent vector space unless the migration strategy is explicit.

Updates are also index-specific. Flat indexes make append and compact operations simple. HNSW supports inserts, but deletion often marks a tombstone because rewiring the graph is costly. IVF can append to lists; many deletes or distribution drift make lists imbalanced. A common design searches an immutable bulk index plus a small mutable fresh index, filters tombstoned IDs at query time, and periodically compacts or fully rebuilds. Permission revocation must update the authoritative filter immediately even if physical deletion and reindexing lag.

Hybrid fusion

Hybrid retrieval first forms a candidate-set union, for example C = topKBM25 ∪ topKdense, then deduplicates by canonical document or passage ID. Fusion can be rank-based or score-based:

RRF(d) = Σ[r ∈ retrievers] 1 / (c + rankᵣ(d)) weighted(d) = α · calibrated_sparse(d) + (1 - α) · calibrated_dense(d)

Reciprocal-rank fusion (RRF) needs no comparable raw scores; c, often around 60, reduces the dominance of rank 1. Weighted fusion can exploit score magnitude, but BM25 is unbounded and query-dependent while cosine is bounded and often tightly clustered. Raw addition can therefore let one retriever dominate after a corpus, query-length, or model change. Calibrate per retriever on held-out queries using rank normalization, z-scores with guarded variance, min-max statistics, or a learned relevance calibration model. Calibration must be versioned and checked by query slice; when distributions drift or a retriever returns very few candidates, RRF is usually safer.

Reranking and latency budgets

A cross-encoder processes each query-candidate pair jointly, enabling token-level interaction and usually stronger precision. Common training objectives are:

  • Pointwise: predict relevance for each pair independently with binary cross-entropy, graded regression, or ordinal loss. It is simple but does not directly optimize ordering.
  • Pairwise: prefer a positive over a negative, for example -log σ(s(q,d⁺) - s(q,d⁻)). It learns relative order but sampling determines which comparisons matter.
  • Listwise: normalize scores across a candidate list and match a target relevance distribution. It best reflects ranking context but costs more memory and depends on constructing representative lists.

The candidate budget determines both the ceiling and the cost: a reranker cannot recover a relevant passage absent from its input, while its compute grows roughly with candidate count and token length. Batch pairs to use accelerators efficiently, bucket by length to reduce padding, and cap both query and passage tokens. Large batches improve throughput but may wait too long at low traffic, so use a short queue deadline and monitor p95/p99 latency.

The retrieval pipeline totals about 49 ms before generation. Within the 30-candidate rerank set, suppose passage A was first-stage rank 1 but merely defines “vector database” and receives cross-encoder score 1.1; passage B was rank 7, directly answers the query, and scores 4.6; passage C was rank 12, gives a relevant benchmark, and scores 3.9. Reranking produces B, C, A; the final selector keeps B and C, then fills three slots with non-duplicate evidence. This improves precision without asking the cross-encoder to score all one million documents.

If the reranker times out, a low-risk fallback can return the fused first-stage order, record degraded mode, and lower the answer-confidence signal. For security-sensitive or high-stakes queries, fail closed or abstain rather than silently changing ranking semantics. Define separate behavior for an unavailable dense index, sparse index, metadata service, and reranker.

Metrics

Recall@k = |relevant ∩ top-k| / |relevant| Precision@k = |relevant ∩ top-k| / k RR(q) = 1 / rank of first relevant result; MRR = meanq RR(q) DCG@k = Σ[i=1…k] (2^relᵢ - 1) / log₂(i + 1) nDCG@k = DCG@k / ideal_DCG@k

Recall@k measures evidence coverage and is the key ceiling before reranking; define how queries with no labelled relevant item are handled. Precision@k measures result purity. MRR emphasizes the first relevant result and ignores later relevant items. nDCG rewards putting highly graded evidence early and works well when relevance is not binary.

Final answer quality is not a clean retrieval metric. A capable model may answer from parametric memory despite bad retrieval, while a weak generator may fail despite perfect evidence. Maintain versioned, labelled retrieval sets with pooled judgements from multiple systems, hard negatives, domain terminology, freshness cases, and sufficient coverage of all relevant passages. Evaluate first-stage recall, post-rerank ordering, and final RAG answer quality separately.

Report paired confidence intervals for system differences, preferably by bootstrap resampling whole queries rather than individual documents; also report the number of queries and practical effect size. Inspect query slices for length, language, rare identifiers, temporal freshness, ambiguous intent, multi-hop evidence, document type, tenant, and permission regime. Averages can improve while a critical slice regresses, so predeclare guardrail slices and minimum sample sizes. See evaluation methodology for broader experimental design.

Permission-filter correctness is a hard constraint, not a relevance trade-off. Test that every returned ID is allowed for the requesting principal, including caches, hybrid unions, fallbacks, deleted documents, and adversarial cross-tenant queries. Track unauthorized-result rate with a target of exactly zero, alongside filter-induced recall loss on documents the principal may access. The threat boundary is expanded in security and data leakage.

Online metrics include result clicks, source opens, citation acceptance, downstream task success, reformulation or abandonment, answer escalation, empty-result rate, and p50/p95/p99 latency. These signals are position-biased and confounded by the generator and UI, so compare randomized experiments with guardrails for permission violations, latency, and zero-result regressions; do not treat click-through rate alone as relevance.

Operational concerns

  • index freshness and versioning;
  • approximate-search recall versus latency;
  • hard-negative mining and false negatives;
  • embedding drift after model changes;
  • deduplication of near-identical passages;
  • domain adaptation;
  • multilingual retrieval and tokenization;
  • cache invalidation after permission changes;
  • fallback when the index or reranker is unavailable.

Failure modes

  • dense semantic similarity returning topically related but non-answering passages;
  • lexical retrieval missing paraphrases;
  • filter leakage across users;
  • evaluating only easy random negatives;
  • stale embeddings after document updates;
  • mixed embedding-model versions in one index;
  • score fusion without calibration;
  • expensive reranking causing latency spikes;
  • false negatives corrupting contrastive training.
