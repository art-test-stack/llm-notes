Learning objectives

You should be able to separate prefill and decode, estimate their FLOPs and memory traffic, account for KV-cache memory and placement, explain cache layouts and decoding methods, implement cached GQA, and test position, mask, and batching correctness.

Notation and assumptions

Let B be batch size, S prompt length, T cached length during decode, H hidden size, F MLP intermediate size, L layers, H_q query heads, H_kv KV heads, D_h = H/H_q, and r = H_kv/H_q. One multiply-add counts as two FLOPs. Formulas describe dense decoder layers with SwiGLU and omit embeddings, the final vocabulary projection, normalization, bias, activation, and other lower-order elementwise work unless stated.

Autoregressive generation

A decoder predicts one token at a time. Without caching, every step recomputes keys and values for the whole prefix. A KV cache stores each layer's projected keys and values, so a decode step projects only the new token. The new query must still attend to all visible cached positions: caching removes repeated work, not the linear-in-context read at each step.

Prefill versus decode

Prefill consumes all prompt tokens in parallel and writes the initial cache; decode repeatedly consumes one token per active request and reads a growing cache. Summing decode attention over many generated tokens is still quadratic in the total decoded length, even though caching avoids recomputing old projections and old query rows.

Prefill cost model

Prefill processes all B × S prompt tokens in parallel and creates the initial cache. For one layer:

OperationApproximate FLOPsComment
Q, K, V projections2 B S H² (1 + 2r)Q has width H; K and V each have width rH. For MHA, this is 6BSH².
Attention scores QKᵀ2 B S² HCausal kernels may skip masked work; this is the dense upper estimate.
Stable softmaxroughly 5 B H_q S²Max, subtract, exponentiate, sum, and divide; kernel accounting varies.
Value aggregation PV2 B S² HSame leading matmul cost as scores.
Output projection2 B S H²Concatenated query-head outputs back to width H.
SwiGLU MLP6 B S H FTwo H→F projections plus one F→H; activation is lower order.

Ignoring the softmax and other elementwise terms, the full decoder stack is approximately:

F_prefill ≈ L B [S(4 + 4r)H² + 4S²H + 6SHF]

The linear projections and MLP scale as O(BLSH²) when F = O(H); attention scales as O(BLS²H). Long prompts eventually make attention dominant, while ordinary prompts in large models can still be MLP-heavy. Large matrices reuse weights and activations well, so prefill is commonly compute-bound.

Explicit prefill estimate

For B=1, S=2,048, L=32, H=4,096, F=11,008, H_q=32, and H_kv=8 (r=0.25): QKV projections cost about 3.30 TFLOPs, scores 1.10 TFLOPs, value aggregation 1.10 TFLOPs, output projections 2.20 TFLOPs, and the MLP 17.73 TFLOPs. The total is about 25.4 TFLOPs per prompt, before the vocabulary head and lower-order operations. This is an operation count, not a latency prediction.

Decode cost model

At one-token decode, replace S by one for projections, but attend over the growing cache of length T. For one layer and one decode step:

  • new-token QKV projections: 2 B H²(1 + 2r) FLOPs;
  • attention score plus value aggregation: 4 B T H FLOPs, plus roughly 5 B H_q T for softmax;
  • output projection: 2 B H² FLOPs;
  • SwiGLU MLP: 6 B H F FLOPs.
F_decode_step ≈ L B [(4 + 4r)H² + 6HF + 4TH]
KV_read_step  ≈ 2 B L T H_kv D_h s_cache bytes
weight bytes per step ≈ P × s_weight                 # weights read once for the batch
weight bytes per produced token ≈ P × s_weight / B  # ideal batch amortization

For the example above at T=4,096, one decode step is about 13.5 GFLOPs per sequence (excluding the vocabulary head and elementwise work) and reads 512 MiB of fp16 KV data per sequence. A 7B model in fp16 also exposes about 14 GB of weights to the step; at batch one, an idealized ≈14 GFLOP / 14.5 GB gives only about 1 FLOP/byte. Batching amortizes the weight read, but every sequence still reads its own cache.

That low arithmetic intensity leaves tensor cores underfed: decode is often limited by HBM bandwidth rather than peak FLOPs. Small one-token matrix shapes also launch many short kernels, so launch latency, synchronization, request scheduling, and CPU dispatch can matter. Kernel fusion, CUDA graphs, continuous batching, weight quantization, and paged attention target these costs; none changes the semantic requirement to read visible K/V.

KV-cache accounting

For scalar size s_cache bytes:

M_KV = 2 × B × L × T × H_kv × D_h × s_cache

The factor two stores keys and values. Standard MHA has H_kv=H_q; GQA shares each KV head across a group of query heads; MQA has H_kv=1. Relative to MHA at the same H_q and D_h, cache capacity and cache-read bandwidth scale by H_kv/H_q.

  • Dtype and quantization: fp32, fp16/bf16, int8, and lower-bit caches use roughly 4, 2, 1, and fewer than 1 data bytes per element. Quantized layouts also store scales (often per head or block) and may require padding; include that metadata and dequantization cost.
  • Sliding window: replace T by the retained window W for sliding-attention layers. Global-attention layers and persistent prefix tokens still need separate accounting.
  • Tensor parallelism: when KV heads are sharded, each TP rank holds roughly 1/TP of the layer cache. If H_kv < TP, implementations may replicate KV heads to avoid awkward collectives, so the saving is not automatic.
  • Pipeline parallelism: each stage stores cache only for its local layers, but every stage needs capacity for the same active requests. The tightest stage determines capacity.
  • Beam search: physically copying K/V for every beam multiplies cache by beam width. A block table can share immutable prompt and common beam-prefix blocks, then use copy-on-write after branches diverge. Logical beam reordering should update references, not move all K/V bytes.

Numerical cache and concurrency example

Take the same 32-layer GQA model with H_kv=8, D_h=128, fp16 cache (s_cache=2), and T=4,096:

M_KV/request = 2 × 32 × 4,096 × 8 × 128 × 2
             = 536,870,912 bytes = 512 MiB

80 GiB GPU - 14 GiB weights - 6 GiB runtime/workspace = 60 GiB cache budget
maximum resident requests ≈ floor(60 GiB / 0.5 GiB) = 120

This 120-request figure is a capacity ceiling at exactly 4,096 cached tokens, not a throughput promise; fragmentation, block metadata, longer sequences, temporary activations, and safety margin reduce production concurrency. At the same shape, MHA (H_kv=32) needs 2 GiB/request and fits about 30; MQA needs 64 MiB/request and fits about 960. An int8 GQA cache roughly doubles the 120 ceiling before scale overhead, while a 1,024-token sliding window roughly quadruples it for purely windowed layers.

Cache layouts and lifecycle

LayoutMechanismTrade-off
ContiguousReserve [L,B,H_kv,T_max,D_h] or per-request contiguous buffers and write at the current offset.Simple addressing and good locality, but internal waste from unused capacity; growth or compaction may copy large tensors.
PagedStore fixed-size physical K/V blocks in a pool. Each request owns a logical sequence of block IDs.Near-on-demand allocation, cheap sharing and reordering; block-table lookup and partially filled tail blocks add overhead.
Ring bufferFor a window W, write position t into physical slot t mod W.Constant memory and no shifting; attention must read wrapped segments in logical order and protect non-evictable prefix/global tokens.

A block table maps (request, logical_block) to a physical block. Allocation appends blocks; eviction decrements references and returns blocks to a free list only when the reference count reaches zero. Policies can evict completed or cancelled requests immediately, reclaim recomputable prefix-cache entries under pressure, or reject/preempt work before corrupting a live sequence.

Dynamic-batch and beam reordering

Suppose batch rows [A,B,C] become [C,A] after B finishes. A contiguous batch-major cache must gather rows [2,0] consistently at every layer, together with lengths, positions, RNG state, stop state, and output buffers. A paged cache instead changes the scheduler's request-to-block-table mapping to [table_C, table_A]; physical K/V blocks do not move. Beam parent selection is the same operation with repeated indices: duplicate table references, increment reference counts, and copy only a shared tail block if a child needs to append to it.

After speculative decoding proposes k tokens and the verifier accepts only a, set the logical length back by k-a, free any now-unreachable whole blocks, and reset the tail-block write offset. Bytes beyond the new length may remain physically present but must be masked and overwritten before reuse. Roll back positions, sampled-token buffers, RNG/counter state where applicable, and stop state with the same transaction; stale table entries or lengths can leak rejected tokens into later attention.

Decoding methods

  • Greedy: choose argmax(logits). Deterministic, cheap, and locally optimal, but it cannot recover from an early poor choice.
  • Temperature: sample from softmax(logits / τ). Lower τ sharpens; higher τ flattens. Treat τ=0 as greedy instead of dividing by zero.
  • Top-k: retain the k highest logits and mask the rest before normalization. The candidate-set size is fixed.
  • Top-p (nucleus): sort by descending probability and retain the smallest prefix whose cumulative mass reaches p, including the threshold-crossing token. Candidate-set size adapts to uncertainty.
  • Beam search: retain the highest-scoring partial sequences, usually with length normalization. It is search, not sampling, and expands compute and cache state with beam width.
  • Constrained decoding: mask tokens that are invalid under a grammar, automaton, schema, or lexical constraint. Apply constraints before sampling and define behavior when the allowed set is empty.

For numerical stability, perform filtering in logit space, compute z = logits/τ, subtract max(z), exponentiate in fp32, normalize with an fp32 sum, then sample. An implementation may use stable log-softmax or a fused kernel, but should never exponentiate raw large logits. Each request needs an independent RNG stream or counter keyed by request and token index so dynamic rebatching does not silently change its samples. Keep EOS tokens, stop strings/automata, generated length, maximum length, and finished/cancelled flags per request; mask finished rows or remove them without borrowing another request's state.

Prefix and prompt caching

A prefix-cache hit is valid only when the cached K/V has the same semantics as fresh prefill. A safe identity key includes:

  • the exact token IDs, not merely prompt text;
  • tokenizer identity and version, special-token policy, and chat-template identity/version;
  • model checkpoint and architecture version plus adapter/LoRA version and any cache-affecting runtime mode;
  • KV dtype/quantization scheme and compatible kernel/layout version;
  • position semantics: absolute offset, position IDs, RoPE configuration/scaling, and any sliding-window or global-token policy.

Hashing rendered text alone is unsafe because tokenization and templates can change. Store collision-resistant content keys and verify token boundaries. Share complete immutable blocks across requests and use reference counts. If a request appends into a partially filled shared block, copy that block first (copy-on-write); otherwise it would mutate every request that references the prefix. The suffix gets private blocks, while the common prefix remains shared.

Cached GQA attention pseudocode

The pseudocode below keeps KV heads grouped instead of materializing repeated K/V. length[b] is the number of cached tokens before this call; requests may have unequal lengths.

# x:           [B, 1, H]
# Wq:          [H, Hq*Dh]       Wk, Wv: [H, Hkv*Dh]
# block_table: [B, max_blocks]   length, position: [B]
# G = Hq // Hkv; require Hq % Hkv == 0

def cached_gqa(x, Wq, Wk, Wv, Wo, cache, block_table, length, position):
    B = x.shape[0]
    q = (x @ Wq).view(B, 1, Hq, Dh).transpose(1, 2)   # [B,Hq,1,Dh]
    k = (x @ Wk).view(B, 1, Hkv, Dh).transpose(1, 2)  # [B,Hkv,1,Dh]
    v = (x @ Wv).view(B, 1, Hkv, Dh).transpose(1, 2)  # [B,Hkv,1,Dh]

    q, k = apply_rope(q, k, position)                 # position[b] == length[b]
    cache.write(block_table, length, k, v)             # append one slot/request
    K, V, valid = cache.gather(block_table, length + 1)
    # K,V: [B,Hkv,Tmax,Dh]; valid: [B,1,1,1,Tmax]

    q = q.view(B, Hkv, G, 1, Dh)                       # map G Q heads/KV head
    score = einsum("bhgqd,bhtd->bhgqt", q, K) / sqrt(Dh)
    score = where(valid, score, -inf)                  # hide padding/unwritten slots
    prob = softmax(score.float(), dim=-1).to(x.dtype)  # stable fp32 reduction
    ctx = einsum("bhgqt,bhtd->bhgqd", prob, V)        # [B,Hkv,G,1,Dh]
    ctx = ctx.reshape(B, Hq, 1, Dh).transpose(1, 2).reshape(B, 1, H)
    return ctx @ Wo, length + 1                        # [B,1,H], updated lengths

Real paged-attention kernels gather logically rather than materializing dense K and V; the shapes above specify semantics. During prefill, write only real prompt tokens. For padded batches, derive each request's position from its valid-token count, not the padded tensor width.

Correctness tests

def test_cached_matches_uncached(model, prompts):
    # Fixed weights, eval mode, no sampling; compare every generation step.
    full_ids = prompts
    cache = empty_cache()
    for step in range(8):
        ref = model(full_ids, use_cache=False).logits[:, -1]
        got, cache = model(full_ids if step == 0 else full_ids[:, -1:],
                           cache=cache, use_cache=True)
        assert allclose(got[:, -1], ref, atol=2e-5, rtol=2e-4)
        full_ids = append(full_ids, argmax(ref, dim=-1))

def test_unequal_prompts(model):

def test_position_offset_and_mask(model):
    # Continuing a prefix at position p must match an uncached prefix+token pass.
    prefix = ids[:11]
    cache = prefill(model, prefix, position=arange(11))
    got = decode(model, ids[11], cache, position=11)
    ref = model(ids[:12], position=arange(12), use_cache=False).logits[-1]
    assert_close(got.logits[-1], ref)

Run equivalence tests in fp32 first, then use documented dtype-specific tolerances. Also cover GQA head grouping, cache growth across block boundaries, ring-buffer wraparound, maximum length, EOS per request, dynamic-batch reordering, beam parent reordering, prefix copy-on-write, and speculative rollback. A useful failure-localization rule: divergence on the first cached token suggests mask/shape/head mapping; divergence only after later tokens suggests write offsets, position increments, reorder state, or rollback.

Failure modes

  • concatenating or gathering the cache on the wrong axis;
  • overwriting cache positions or exposing unwritten padding;
  • applying RoPE twice, resetting offsets, or reusing a prefix under incompatible position semantics;
  • materializing repeated GQA K/V unnecessarily;
  • reordering K/V without reordering lengths, block tables, RNG, and stop state;
  • freeing shared blocks without reference counting or mutating them without copy-on-write;
  • retaining finished requests in active batches or letting them consume another RNG stream;
  • assuming cache quantization changes only bytes while ignoring scale metadata and kernel support;
  • claiming caching changes dense-attention asymptotics rather than avoiding recomputation.
