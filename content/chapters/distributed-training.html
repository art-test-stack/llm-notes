Learning objectives

You should be able to reason from state placement and communication, explain DDP and FSDP/ZeRO execution, account for memory, diagnose collective failures, and design data and checkpoint semantics across ranks.

Four questions for any distributed design

  1. What is partitioned: data, parameters, tensor dimensions, layers, sequence, experts, or requests?
  2. What is replicated: parameters, optimizer state, activations, KV cache, or complete serving instances?
  3. What communication occurs: all-reduce, all-gather, reduce-scatter, all-to-all, broadcast, or point-to-point?
  4. Which bottleneck is being solved: capacity, throughput, latency, context length, or concurrency?

Collective primitives

Primitive Effect Typical use
Broadcast root sends the same value to all ranks initialization and metadata
All-reduce reduce values and return result to all ranks DDP gradients, row-parallel outputs
All-gather collect all shards on every rank FSDP parameter materialization
Reduce-scatter reduce then leave one shard per rank sharded gradients or activations
All-to-all every rank sends distinct slices to every rank MoE token dispatch
Send/receive point-to-point transfer pipeline activations and gradients

All participating ranks must call compatible collectives in the same order. Rank-divergent control flow, dtype/shape mismatch, or one rank performing fewer iterations can hang the job.

Collective cost model

Use the simple \alpha -\beta model: \alpha is the fixed startup latency of one communication step, \beta is seconds per byte (inverse effective bandwidth), p is the number of ranks, and N is the tensor size in bytes. These formulas describe idealized per-rank critical-path cost; protocol overhead, contention, topology, and imperfect chunking make real measurements worse.

A ring all-reduce decomposes into a reduce-scatter followed by an all-gather. Split the tensor into p chunks of N/p bytes. In each phase, every rank performs p−1 neighbor exchanges:

T_reduce-scatter ≈ (p−1)α + ((p−1)/p)Nβ T_all-gather ≈ (p−1)α + ((p−1)/p)Nβ T_ring-allreduce ≈ 2(p−1)α + 2((p−1)/p)Nβ

Therefore each rank sends and receives 2(p−1)N/p bytes for ring all-reduce, approaching 2N in each direction as p grows. Network-wide sent volume is 2(p−1)N. For example, with four ranks and a 1 GiB gradient, each rank sends 2 \times 3/4 \times 1 = 1.5 \text{GiB}: 0.75 GiB in reduce-scatter and 0.75 GiB in all-gather.

Rings are bandwidth-efficient for large tensors because every link can stream chunks, but their O(p) startup steps hurt small messages. Tree or recursive-doubling collectives use roughly O(\operatorname{log} p) rounds and usually win when latency dominates; depending on the algorithm they may move larger messages on some links or use bandwidth less evenly. Libraries select hierarchical algorithms by message size and topology—for example, reduce within a node over NVLink/NVSwitch, then across nodes over the fabric, then broadcast locally.

Unsharded Adam mixed-precision training often requires roughly 12–20 bytes per trainable parameter before activations, depending on dtype choices and retained master copies. Activation memory then grows with microbatch, sequence length, hidden size, and layer count.

DDP

Each rank stores a complete model replica, processes distinct data, runs local forward/backward, and synchronizes gradient buckets with all-reduce. Every rank then applies the same optimizer update.

Execution timeline

time →
forward:       [layer 1][layer 2][layer 3][layer 4]
backward:                                  [L4][L3][L2][L1]
parameter ready:                            ↓   ↓   ↓   ↓
bucket A all-reduce:                            [launch======]
bucket B all-reduce:                                    [launch======]
optimizer step:                                                    [step]

Autograd discovers gradients in reverse execution order. DDP marks each parameter ready; when every gradient assigned to a bucket is ready, it launches that bucket's all-reduce while earlier layers are still backpropagating. The optimizer must wait for all buckets. A larger bucket amortizes \alpha and uses bandwidth well but becomes ready later and reduces overlap; a smaller bucket launches sooner but pays more latency and scheduling overhead.

  • no_sync() accumulates local gradients without collectives on early microsteps; leave the final microstep synchronized. It saves communication launches, not gradient or optimizer memory.
  • A static graph lets DDP reuse the same readiness/order assumptions and avoid repeated graph discovery, but requires stable parameter usage and control flow.
  • With unused parameters, DDP may need graph traversal to pre-mark them ready. Rank-dependent usage can produce mismatched reductions or gradients with different meanings; static-graph promises must not be violated.
  • The slowest rank controls every bucket. Late input, a slow kernel, thermal throttling, or a bad network path creates exposed communication and idle time on all peers.

DDP does not shard input automatically, reduce parameter/optimizer memory, or make a model fit when one replica exceeds one GPU. A common silent bug is every rank reading the same examples, which preserves execution while reducing effective data diversity.

Execution timeline for full sharding

forward:  AG(block 1) → compute 1 → reshard 1 → AG(block 2) → compute 2 → reshard 2
backward:                         AG(block 2) → grad 2 → RS(grad 2) →
                                  AG(block 1) → grad 1 → RS(grad 1) → local update
AG = parameter all-gather; RS = gradient reduce-scatter

With reshard-after-forward enabled, full parameters are freed after each forward block and gathered again for backward: lower temporary residency, more communication. Disabling it retains materialized parameters through backward: fewer gathers, higher peak memory. Forward prefetch can gather the next block while the current block computes; backward prefetch does the analogous overlap around reverse-order execution. Prefetch too aggressively and several all-gathers coexist, turning an optimization into an OOM.

Wrap granularity defines the unit of gathering, freeing, and prefetch. Tiny wraps cause many latency-bound collectives; huge wraps materialize large parameter sets and reduce overlap opportunities. Transformer blocks are a common starting point, then measured traces decide. The critical FSDP fit calculation is:

peak ≈ persistent local shards + current full wrapped unit + any prefetched next unit + activations, gradients, buckets, and kernel workspaces

Thus a model with small persistent shards can still OOM during a transient all-gather. Treat parameter dtype, reduction dtype, and buffer dtype as independent policies: low-precision parameters save gather bandwidth and compute memory; an FP32 reduction may improve robustness at more traffic; buffers such as normalization statistics need an explicit policy rather than inheriting by accident.

ZeRO and offload

ModeOptimizer stateGradientsParameters
ZeRO-1shardedreplicatedreplicated
ZeRO-2shardedshardedreplicated
ZeRO-3shardedshardedsharded

ZeRO-3 and FSDP full sharding share the core state-partitioning idea, though APIs, scheduling, and checkpoint formats differ. Offload adds a slower storage tier:

  • CPU optimizer offload: keep moments and often the update on host memory; saves substantial HBM but pays GPU↔CPU copies and CPU update time.
  • Parameter offload: keep parameter shards in host memory until needed; increases transfer demand on every materialization.
  • NVMe offload: extends capacity beyond DRAM, but requires staged NVMe↔DRAM↔GPU movement, deep buffering, and predictable sequential I/O.

Offload helps when capacity is the binding constraint and compute is long enough to hide movement. It is counterproductive when PCIe, CPU memory bandwidth, NVMe, or the network is already saturated; when layers are too small to hide latency; or when extra transfers contend with inter-node collectives. A job that fits with checkpointing, a smaller microbatch, or better sharding usually runs faster without offload.

Activation checkpointing

MethodSaved stateCost and use
Full-block checkpointingblock inputs/boundariesrecomputes almost the whole block; simple and large memory saving
Selective checkpointingexpensive or reuse-worthy intermediatesrecomputes cheap operations while retaining costly ones; better trade-off, more planning
Partitioned activationsonly a shard per parallel rankreduces replicated activation memory but adds gather/scatter or topology constraints

If the original forward costs F and checkpointed regions add recomputation R, the forward-work factor is (F+R)/F; checkpointing every block often makes R approach F, while total step FLOPs rise by less because backward already dominates. RNG state for dropout and other stochastic operations must be preserved or deterministically regenerated so recomputation uses the same masks; otherwise the backward pass differentiates a different function.

With pipeline parallelism, activation lifetime also depends on the number of in-flight microbatches. Checkpointing can make more microbatches fit and shrink the bubble, but recomputation lengthens stage service time and may shift the bottleneck. Align checkpoint regions with stage boundaries so recomputation does not require remote activations that were already discarded. See parallelism strategies for pipeline schedules.

Data path

The model can be distributed correctly while the data path is wrong or slow. Requirements include:

  • non-overlapping samples per data-parallel rank unless replication is deliberate;
  • epoch/rank-aware shuffling;
  • compatible step counts;
  • explicit packing and document-boundary semantics;
  • bounded prefetching;
  • measured input-wait time.

GPT-Lab assigns Parquet row groups by rank. This is simple and deterministic for fixed world size, but row-group counts do not guarantee token balance. Changing world size changes ownership and therefore replay semantics.

For equal fixed-length local batches, the token-slot count is:

token slots/update = device_batch × sequence length × world size × accumulation steps

This special case assumes equal batches and unique data across ranks. The general effective supervised-token count is the sum of loss-contributing mask entries across every rank and accumulation microstep. Input-token count, non-padding-token count, and supervised target-token count can differ. For example, two ranks with one length-8 slot each have 16 slots; if their non-padding lengths are 8 and 5 and response-only masks supervise 3 and 2 targets, the update contains 13 non-padding input tokens but only 5 supervised tokens.

Loading, tokenization, packing, and replay semantics are developed further in Pretraining Data Systems. The chosen global token batch also changes the optimization regime and compute allocation discussed in Scaling Laws and Compute-Optimal Training.

Topology and failures

A process group defines exactly which ranks participate in a collective. Hybrid jobs create separate groups for data/FSDP, tensor, pipeline, context, or expert parallelism. Rank mapping should put frequent, high-volume communication on the fastest links: tensor parallelism within NVLink/NVSwitch domains, then less frequent data-parallel traffic across NICs when possible. Local rank, global rank, node, GPU, NUMA domain, and NIC affinity all matter; consecutive rank numbers do not guarantee physical proximity.

  • NCCL timeout: a watchdog reports that a collective exceeded its deadline. The timeout is evidence, not necessarily the cause; inspect the earliest slow or missing rank.
  • Collective mismatch: ranks call different operations, shapes, dtypes, counts, or order. Log a monotonically increasing collective/step identifier and compare all ranks.
  • Dead rank: process crash, OOM, hardware error, or lost node prevents peers from completing. Ordinary collectives cannot heal around it; tear down the affected group/job.
  • Elastic recovery: a coordinator detects membership loss, chooses a new world size/rank assignment, rebuilds every process group, restores a globally complete checkpoint, and reconstructs the data schedule. In-flight work is discarded.
  • Straggler: one live rank arrives late. Compare per-rank input wait, forward/backward kernel time, collective enqueue/completion, GPU clocks, errors/retries, NIC counters, and data-shard token counts. Correlate the first divergence rather than the final timeout.

Distributed checkpointing internals

Each rank writes bounded shards of model and optimizer tensors instead of gathering everything on rank 0. Global metadata records tensor names, full shapes, dtypes, shard offsets, replication, model configuration, optimizer parameter identity, and format version. A manifest maps logical tensors to shard files and checksums.

  1. Write every shard to a unique temporary path and flush it as required by the storage system.
  2. Collect shard sizes/checksums and validate that all required global tensor ranges are covered exactly once.
  3. Write the manifest last, also through a temporary path.
  4. Atomically publish a small completion marker or rename the manifest. Readers accept only checkpoints with that marker and a valid manifest.

Missing temporary files, checksum mismatches, overlapping/gapped ranges, or an absent completion marker detect partial writes. A directory merely existing is not proof of a usable checkpoint.

Changed-world-size example: 8 ranks to 4

Suppose an optimizer moment tensor has global shape [8192, 4096] and was saved as eight row shards, each covering 1024 rows. On restore with four ranks, new rank 0 reads old row ranges [0,1024) and [1024,2048), concatenates or streams them into its new [0,2048) shard; ranks 1–3 do the same for the next pairs. This works because the manifest describes global coordinates, not “rank 0's opaque state.” A resharder may read directly from several old files so no rank materializes the full tensor.

Optimizer portability is harder than weight portability: moments and master weights must be keyed to stable parameter identities and retain compatible shape, dtype, step counters, and optimizer hyperparameters. Flattened or reordered parameters need mapping metadata. Some optimizer layouts cannot be converted without a purpose-built migration.

Model and optimizer recovery can be exact while data replay remains approximate. Worker prefetch queues, streaming-source cursors, randomized packing buffers, and partially consumed batches may not be serialized. After an elastic world-size change, sample ownership changes even when the global token counter is restored; document whether the loader guarantees exact replay, at-least-once replay, or only statistically equivalent continuation.

Start by reproducing single-rank correctness, then verify unique rank-local data and equal step counts, then compare distributed numerics, and only then tune communication. For low-level compute gaps, continue with torch.compile, Custom Kernels and GPU Performance.

Failure modes to remember

  • duplicate data on all ranks;
  • collective mismatch or rank divergence;
  • synchronizing every accumulation microstep;
  • unused parameters on only some ranks;
  • rank-0 gathering that exhausts memory;
  • transient FSDP peaks misunderstood as persistent state;
  • topology-unaware placement;
  • checkpoint format tied to one world size;
  • reporting weak scaling as strong scaling.
