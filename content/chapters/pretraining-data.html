Learning objectives

You should be able to describe the complete pretraining-data pipeline, compute the effective token batch, reason about mixture weights and replay, explain document packing and rank sharding, and identify contamination, duplication, and recovery failures.

Training-stage context

Stage Main question Typical data Objective
Pretraining Can the model predict and represent language? large unlabeled corpora token cross-entropy
Continued pretraining Can it acquire a domain, language, format, or context length? focused unlabeled corpora language-model objective
SFT Can it respond in the desired interface? prompt-response demonstrations response-token cross-entropy
Preference optimization Does it prefer better responses? chosen/rejected pairs pairwise preference loss
Online RL Can behavior improve through rewarded exploration? prompts, rollouts, rewards policy-gradient objective

For causal language modeling:

L_NLL(θ) = -Σ_t log p_θ(x_t | x_<t)

This learns syntax, semantics, corpus knowledge, code and mathematical patterns, and reusable representations. It does not by itself guarantee instruction following, truthfulness, safety, calibration, or stable dialogue.

Pipeline

A production pipeline usually performs:

acquisition → parsing → normalization → classification → quality filtering
→ exact/near deduplication → privacy/licensing checks → contamination checks
→ mixture weighting → sharding → tokenization → packing

Raw token count is not useful token count. Boilerplate, duplicates, SEO text, malformed code, and low-quality synthetic text can consume compute while adding little generalization.

End-to-end pipeline

Stage Input and operation Persisted output Critical check
1. Acquire Raw document plus source response Immutable content ID, source URI, fetch time, license metadata Can this exact artifact be traced, blocked, or removed?
2. Parse Decode HTML, PDF, code, or other source format Text, structural fields, parser version, parse status Did parsing silently drop text or join unrelated fields?
3. Normalize and classify Unicode and whitespace normalization; language and source classification Canonical text and labels without overwriting the raw artifact Are normalization rules versioned and language-aware?
4. Filter and redact Quality, boilerplate, SEO, PII, malware, policy, and license checks Accepted or rejected document, reason codes, redaction map Can acceptance and every rejection reason be reproduced?
5. Deduplicate Exact hashes, normalized hashes, MinHash/LSH candidates, span matching Duplicate cluster ID, representative, similarity score, decision Are legitimate templates or repeated code being over-removed?
6. Decontaminate Compare against validation and benchmark registries Match type, benchmark ID, evidence, quarantine decision Were solutions, translations, and paraphrases checked too?
7. Mix and shard Assign sampling weights, shuffle deterministically, write shards Mixture version, shard manifest, document-to-shard mapping Do measured token exposures match intended weights?
8. Tokenize Apply a pinned tokenizer and boundary policy Token IDs, document boundaries, token counts Are tokenizer version and language-specific fertility recorded?
9. Pack Fill fixed-length rows from tokenized documents Packed sequence, segment metadata, loss and attention masks Are boundary semantics, padding, and cross-document attention intentional?

The last two stages depend on the choices described in Tokenization and Vocabulary Design. Synthetic records should retain their generator and verifier lineage as described in Synthetic Data Generation and Filtering.

Data-quality dimensions

  • correctness and factuality;
  • domain, task, style, language, and difficulty diversity;
  • exact and near-duplicate rate;
  • benchmark decontamination;
  • provenance, licensing, privacy, and removal requirements;
  • formatting and chat-template consistency;
  • language-specific token fertility;
  • verifier precision for generated or filtered data.

Near-deduplication must be tuned carefully. Aggressive matching can remove legitimate repeated code or standard legal/technical templates; weak matching leaves memorized copies across training and validation.

Exact and near deduplication

Deduplication has three distinct operating points:

Kind What counts as a match Typical mechanism Main risk
Exact Identical raw bytes or canonical text Cryptographic or fast content hash Misses trivial formatting changes
Near Large lexical overlap after small edits Shingles, MinHash, Jaccard similarity, and LSH Can remove legitimate repeated structure
Semantic Same meaning despite paraphrase or translation Embedding retrieval followed by a stronger verifier Expensive and prone to topic-level false positives

Exact deduplication. Hash raw bytes to catch identical artifacts, then hash normalized text to catch copies that differ only in Unicode form, whitespace, line endings, casing where appropriate, or removable markup. Preserve both hashes and the normalization version: aggressive normalization can collapse distinct source code, tables, or languages. Hash collisions are rare but operational decisions should still retain the candidate IDs and representative text for audit.

Near deduplication. Split normalized text into word or character n-gram shingles. For shingle sets A and B, Jaccard similarity is J(A,B) = |A ∩ B| / |A ∪ B|. MinHash provides a compact estimate of this similarity; locality-sensitive hashing (LSH) buckets signatures so that only plausible pairs receive an exact similarity check. LSH is candidate generation, not the final removal rule.

Document-level deduplication chooses one representative from a duplicate cluster and is cheap to reason about, but it misses copied chapters, functions, or answer spans embedded in otherwise different documents. Span-level deduplication removes or masks matching regions and retains unique context, but boundary errors can damage syntax and make provenance harder. Many systems use document-level removal first, then span-level checks for long or high-risk material.

Thresholds should be calibrated on labeled pairs stratified by language, source, length, and format. Short documents need special handling because a few common shingles can produce high similarity. Review both false negatives and false positives near the threshold. Whitelist or downweight evidence from license headers, legal clauses, navigation templates, generated API clients, and common code idioms so legitimate repetition is not erased merely because it is conventional.

Cross-split deduplication is asymmetric: freeze validation and test sets, search training candidates against them, and remove or quarantine the training copy. Run it after every material normalization, filtering, or dataset refresh because transformations can reveal matches that raw hashes missed. Also deduplicate within validation so a repeated example does not make uncertainty estimates look better than they are.

Filtering and provenance

  • Language identification: use document- and span-level labels with confidence scores; code-switching, short text, transliteration, and code require an unknown or mixed class rather than a forced label.
  • Heuristic quality filters: reject parse failures, extreme symbol ratios, repeated lines, truncation, implausible language statistics, or too little natural text. Record each rule separately so one broad reject flag does not hide regressions.
  • Learned quality classifiers: rank or gate documents using labeled quality data, but audit calibration by language and domain. A classifier trained on polished prose can incorrectly suppress dialects, forums, code, or specialist writing.
  • Boilerplate and SEO filtering: remove menus, cookie banners, link farms, keyword stuffing, scraped snippets, and templated page chrome while retaining the main content and its structure.
  • PII detection and redaction: combine deterministic detectors for structured identifiers with contextual models for names, addresses, and secrets. Prefer reversible audit metadata without retaining the sensitive value in ordinary logs.
  • Malware and unsafe-code filtering: scan archives and code for payloads, credentials, exploit instructions, obfuscation, and suspicious binaries. Detection can tag, quarantine, redact, or restrict access; treating all security-related code as malware would destroy legitimate defensive material.
  • Licensing and source metadata: keep source URI, acquisition time, publisher, declared license, terms snapshot, jurisdiction or policy class, and every transformation version beside a stable content ID.
  • Removal requests and traceability: maintain a lineage graph from source artifact to normalized document, duplicate representative, shard, and dataset release. A tombstone or denylist must be reapplied when a dataset is rebuilt so removed content does not return from a mirror or duplicate cluster.

Filters change the data distribution. Compare accepted and rejected token counts by source, language, domain, and rule; sample false positives from every high-volume rejection path. Provenance is useful only if it survives normalization, deduplication, sharding, and recovery.

Data-mixture mathematics

Let source i contain N_i usable tokens and raw proportion p_i = N_i / Σ_j N_j. The sampling probability q_i is a training decision, not a property of the corpus. A common temperature rule is:

q_i(τ) = p_i^(1/τ) / Σ_j p_j^(1/τ)

At τ = 1, sampling follows raw proportions. For τ > 1, the distribution flattens and smaller sources are upsampled; for τ < 1, it concentrates on large sources. If total training budget is T tokens, expected exposure is E_i = Tq_i and effective epochs are e_i = E_i/N_i. These are expected values: finite shards, without-replacement windows, and packing can perturb the realized totals.

Effective-epoch numerical example

Suppose the cleaned pool contains 800B web tokens, 150B code tokens, and 50B book tokens: raw proportions 0.80, 0.15, and 0.05. With τ = 2, weights are proportional to their square roots and normalize to approximately 0.594, 0.257, and 0.149. For a 1T-token run:

Source Usable tokens N_i Sampling weight q_i Expected tokens Tq_i Effective epochs Tq_i/N_i
Web 800B 59.4% 594B 0.74
Code 150B 25.7% 257B 1.71
Books 50B 14.9% 149B 2.97

The books source is only 5% of raw tokens but supplies almost 15% of training tokens and is seen about three times. Upsampling changes both balance and repeated exposure; track unique tokens, effective epochs, and duplicate clusters, not only requested mixture weights. Token budgets should also be checked against the compute-optimal assumptions in Scaling Laws and Compute-Optimal Training.

During domain adaptation, a mixture can reserve probability α for domain data and 1-α for general replay. General replay reduces forgetting but spends target-domain compute. Select α from target gains, broad-regression limits, and exposure caps rather than from domain loss alone.

Adaptive mixture methods

  • Hand-tuned mixtures: begin with quality, coverage, legal constraints, and exposure caps; run ablations around a small number of interpretable weights. They are simple to audit but expensive to tune at full scale.
  • Proxy-model evaluation: train smaller models or short runs on candidate mixtures and compare held-out slice loss plus downstream tasks. Proxies reduce search cost only when rankings transfer to the target scale, tokenizer, and training horizon.
  • Robust optimization and DoReMi-style weighting: estimate per-domain excess loss relative to a reference and increase weight on domains where the learner underperforms, subject to smoothing or minimum/maximum weights. This targets balanced improvement rather than matching corpus size.

Optimizing only validation loss from a narrow proxy can reward a small, benchmark-like domain, amplify noisy or irreducible groups, or sacrifice capabilities absent from the proxy suite. Keep independent evaluations, provenance constraints, diversity floors, exposure ceilings, and full-scale confirmation. The evaluation contract belongs with LLM Evaluation and Benchmark Design, not inside the mixture optimizer.

Benchmark contamination

Contamination is not identical to ordinary corpus deduplication: the protected benchmark and its lineage are the reference, and matches may appear in prompts, answers, explanations, or derived material.

  • Exact matching: compare raw and canonical hashes for benchmark prompts, reference answers, and official solutions.
  • Normalized n-grams: normalize punctuation, whitespace, markup, and stable boilerplate, then search for distinctive overlapping token or character windows.
  • Fuzzy matching: use edit distance, shingle Jaccard, MinHash/LSH, or longest-common-subsequence evidence to find lightly edited copies.
  • Semantic overlap: retrieve embedding-near candidates, then verify whether they reproduce the task or answer rather than merely share a topic. Semantic similarity alone is insufficient evidence for removal.
  • Temporal holdouts: use tasks created after the training cutoff and verify timestamps and source histories. A late benchmark can still contain older public questions.

Search beyond the benchmark file itself: worked solutions, explanations, answer keys, forum discussions, code repositories, screenshots recovered by OCR, paraphrases, and translated copies can leak the solution signal. For generated benchmarks, trace seed tasks and generator context as well.

False positives are common for short questions, standard definitions, common code, and canonical mathematical statements. An audit should version the detector and protected set, retain match type and offsets, rank candidates by distinctiveness, manually review a stratified sample and every high-impact cluster, quarantine uncertain cases, and report contamination rates both before and after adjudication. Evaluation results should disclose the policy rather than claiming a binary “clean” dataset.

Curricula

Curriculum Schedule Potential benefit Failure mode
Quality Start with highly filtered data, then broaden; or reserve the cleanest data for late training Stable early signal or a clean final phase Classifier bias narrows coverage; late distribution shift destabilizes loss
Domain Change general, language, code, or specialist ratios over time Foundation first, specialization later Forgetting if general replay falls too quickly
Difficulty Move from short/common patterns to rarer or more compositional examples May improve learning efficiency Difficulty scores can proxy length, language, or model familiarity
Sequence length Increase packed length in stages Lower early compute and later long-context exposure Changes memory, positional behavior, packing, and tokens per step

A curriculum changes the optimization problem, not just the input queue. Coordinate phase boundaries with learning-rate schedules, the global token batch, gradient accumulation, and checkpointing. Increasing sequence length at a fixed example batch increases tokens per update; reducing the example batch can instead change gradient noise. Reusing optimizer state across a sharp distribution shift preserves momentum and variance estimates from the old phase, while resetting it discards useful history. Treat either choice as an experiment and log it in the run manifest.

Continued-pretraining mixtures

A small high-quality or underrepresented domain can be upweighted, but repeated epochs increase memorization and overfitting risk. Continued pretraining can use:

  • pure domain continuation for maximum specialization;
  • domain plus general replay to reduce forgetting;
  • curricula that alter quality, difficulty, sequence length, or domain ratio;
  • upsampling of rare high-value sources with exposure monitoring.

Evaluate both target-domain gains and general-capability regression. A lower domain loss is insufficient if broad capabilities collapse.

GPT-Lab data path

The source notes describe:

Parquet shards → ShardManager → row-group assignment by rank
→ lazy tokenization → token-budgeted deque → packed fixed-length batches

Row groups are independently readable and form a natural sharding unit. With world size W, rank r can consume groups r, r+W, r+2W, .... This avoids duplicate row-group consumption only if world size and shard order remain stable.

Trade-offs:

  • small row groups increase metadata and scheduling overhead;
  • large row groups reduce balancing granularity;
  • equal row-group counts do not imply equal token counts;
  • Parquet decode and tokenization can become CPU bottlenecks.

Token-budgeted buffering

A critical GPT-Lab failure was a quantity intended as a token budget being interpreted as a document count. The loader could queue far too many documents before the first batch. The corrected invariant tracks actual buffered tokens and stops refill at a bounded budget.

This is a strong interview example because it is a unit/semantic error, not a complex algorithmic bug. Useful safeguards are named units, assertions, queue-memory telemetry, and tests with extreme document lengths.

Packing documents

Packing produces a stream such as:

[BOS] document A [BOS] document B [BOS] document C ...

It avoids padding and improves useful-token utilization. However, a BOS marker alone does not isolate documents: ordinary causal attention still lets tokens in document B attend to A when they share one sequence row.

Stronger isolation options include block-diagonal masks, segment-aware masks, position reset, one document per row, or BOS-aligned packing. These trade data efficiency and kernel simplicity against semantic isolation.

Global token batch

tokens/update = microbatch × sequence length × accumulation steps × data-parallel world size

This formula assumes each rank receives distinct examples. If rank sharding is wrong, the nominal global batch overstates data diversity.

Recovery semantics

Checkpointing the model and optimizer can be exact, while data replay remains approximate. Exact replay may require:

  • shard, row-group, and document offsets;
  • buffered and partially consumed token sequences;
  • all relevant RNG states;
  • stable shard ordering and world size;
  • deterministic workers and tokenization.

Changing world size changes row-group ownership. State this limitation explicitly rather than claiming bit-exact recovery.

Production observability

Signal Useful breakdown What it detects
Tokens accepted and rejected Reason, source, language, domain, pipeline version Filter drift, classifier outages, accidental source loss
Source exposure Requested versus realized tokens and effective epochs Mixture, sampler, exhaustion, and replay errors
Duplicate rates Exact, normalized, near, span, within/cross split Normalization regressions and memorization risk
Rank imbalance Documents, non-padding tokens, batches, queue depth per rank Stragglers and duplicated or skipped partitions
Data-wait time Read, decode, tokenize, collate, collective wait GPU starvation and misplaced optimization effort
Shard manifests Content hashes, row counts, token counts, schema, build and mixture IDs Silent shard replacement, truncation, or incompatible rebuilds

Dashboards need immutable manifests underneath them. For every checkpoint, record dataset release, shard order, sampler configuration, tokenizer, filter and dedup versions, RNG state, world size, worker count, curriculum phase, and consumed-token counters. This connects data behavior to the failure and throughput analysis in Distributed LLM Training.

Reproducibility has limits: remote sources change, parsers and classifiers evolve, asynchronous workers race, and a changed world size repartitions data. If queued or partially packed examples are not checkpointed, recovery repeats or skips some tokens. Report the replay tolerance that is actually guaranteed—statistical, document-exact, or token-exact—rather than treating a matching model checkpoint as proof of identical data consumption.

Implementation failure modes

  • Normalization-order bug: hashes are computed before boilerplate removal, so copied articles appear unique. Version the canonicalization DAG and test known equivalent pairs.
  • LSH treated as truth: every bucket collision is deleted without exact scoring or representative selection. Re-score candidates and retain cluster evidence.
  • Cross-split direction reversed: a validation item is removed while its training copy remains. Freeze protected splits and make removal asymmetric.
  • Filter feedback loop: a learned quality model prefers text resembling its narrow labels, and retraining on accepted data amplifies the bias. Audit rejected slices and keep independent labels.
  • PII leaked through logs: redacted documents are safe but rejection traces contain the original secret. Store locations and detector categories, not sensitive payloads.
  • Requested weights mistaken for realized weights: exhausted shards, retries, or packing alter exposure. Count emitted non-padding tokens by source after packing.
  • Effective epochs hidden: a small source is repeatedly sampled until it memorizes. Set exposure caps and alert on unique-token reuse.
  • Contamination detector overclaims: semantic retrieval flags topical similarity as leakage. Require match evidence and manual adjudication for ambiguous cases.
  • Resume changes the data stream: only model and optimizer are restored, or world size changes. Persist loader state or document the bounded replay/skipping behavior.
  • Equal rows assumed balanced: ranks get equal row groups but unequal tokenization cost and token counts. Measure tokens and wait time per rank.

Validation checklist

  • language/domain distributions before and after filtering;
  • duplicate rates and train-validation leakage after normalization;
  • benchmark overlap;
  • tokens per source and repeated exposure;
  • token fertility and sequence-length distributions;
  • packing efficiency and cross-document attention semantics;
  • unique examples per rank;
  • data-wait time and GPU starvation;
  • provenance and access-control metadata.

Review questions

  1. Design exact and near-deduplication for a multilingual web-and-code corpus. Which normalization, shingle, LSH, and threshold choices would you validate?
  2. When should span-level deduplication replace document removal, and how would you avoid deleting license headers, legal language, or common code?
  3. Given source sizes, a temperature, and a total token budget, compute sampling probabilities, expected tokens, and effective epochs.
  4. Design a general-replay mixture for domain continuation. Which target gains and broad regressions determine the replay ratio?
  5. Explain DoReMi-style reweighting and why a small proxy model with one validation loss can choose a harmful mixture.
  6. Audit a benchmark for prompt, solution, explanation, paraphrase, and translated-copy contamination while controlling false positives.
  7. Design a sequence-length curriculum without accidentally changing the global token batch or invalidating optimizer assumptions.
  8. Design a streaming dataset for eight GPUs and explain why row-group balance is not token balance.
  9. Compare packing with padding and block-diagonal masking.
  10. A resumed run has matching model weights but different loss for 200 steps. Diagnose the loader, shard manifest, RNG, worker, and world-size state.
  11. Which production metrics distinguish a slow parser, tokenizer starvation, mixture drift, duplicate ranks, and an over-aggressive quality filter?
