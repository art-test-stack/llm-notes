Learning objectives

You should be able to derive BPE training and encoding, implement Viterbi decoding for a unigram tokenizer, compare major tokenizer families, quantify the vocabulary-size trade-off, and design a leakage-safe tokenizer evaluation. The technical standard is to state the algorithm, its invariants, its asymptotic costs, and the input distributions on which it fails.

Why tokenization matters

A tokenizer is a versioned program that maps text or bytes to token IDs. Its normalization, pre-tokenization, learned model, special-token policy, and decoder are all part of that program. It changes sequence length, attention and activation cost, embedding and output-projection size, multilingual fertility, treatment of code and rare strings, document-boundary semantics, and the numerical scale of token-level loss.

A useful mental model is:

raw input → normalize → pre-tokenize → segment → token IDs
token IDs → token pieces → undo byte/space representation → decoded text

Every arrow needs a specified inverse or an explicitly documented lossy policy. An implementation that shares a vocabulary but changes normalization or pre-tokenization is a different tokenizer.

BPE training versus BPE encoding

Byte-pair encoding has two different algorithms. Training uses corpus frequencies to learn an ordered list of merges. Encoding never recomputes corpus frequencies; it uses the learned merge order as a rank table. Confusing these phases is a common mistake.

Initial alphabet and pre-tokenization

First choose the atomic symbols and the boundaries across which merges are legal:

  • Character BPE starts from characters plus required boundary markers. Characters excluded by a coverage threshold need \lt \text{unk}\gt or byte fallback.
  • Byte-level BPE starts from all 256 byte values, usually mapped reversibly to displayable code points. It has no unknown byte.
  • Classic subword BPE pre-tokenizes words and prevents cross-word merges, often using an end-of-word marker.
  • A GPT-style regular-expression pre-tokenizer forms chunks before byte-level BPE. SentencePiece can instead learn from raw sentences and represent a space with a visible marker such as ▁.

Pre-tokenization is not cosmetic: forbidding merges across a boundary changes both pair counts and the set of strings the learned vocabulary can represent as one token.

Pair-frequency counting and iterative merge selection

Represent the corpus as a multiset of symbol sequences. At each iteration, sum the weighted count of every adjacent pair, select one pair, replace all non-overlapping occurrences with a new symbol, append that pair to the merge list, and update counts. Stop at the requested vocabulary size, merge budget, or minimum frequency.

def train_bpe(word_counts, merge_budget):
    # word_counts: {tuple(initial_symbols): corpus_frequency}
    merges = []
    for rank in range(merge_budget):
        counts = Counter()
        for symbols, weight in word_counts.items():
            for pair in adjacent_pairs(symbols):
                counts[pair] += weight
        if not counts:
            break

        # Concrete reproducibility rule: highest frequency, then lexical pair.
        best = min(counts, key=lambda pair: (-counts[pair], pair[0], pair[1]))
        word_counts = {
            merge_all_nonoverlapping(symbols, best): weight
            for symbols, weight in word_counts.items()
        }
        merges.append(best)                 # list position is the merge rank
    return merges

Tie handling is part of the model format. Lexicographic order is one valid rule; first occurrence in a stable corpus traversal is another. Parallel reductions, hash iteration, or locale-dependent string comparison must not silently choose a winner. Persist the resulting ordered merge list, not just the final vocabulary.

For an overlapping pair such as (a,a) in a a a, replacement must be defined, normally left-to-right and non-overlapping, producing aa a. Trainer and runtime must share this convention.

Complete worked example

Use the pre-tokenized corpus below, where \lt /w\gt is an end-of-word symbol and the number is the word frequency:

low    × 5  →  l o w </w>
lower  × 2  →  l o w e r </w>
newest × 6  →  n e w e s t </w>
widest × 3  →  w i d e s t </w>

The largest initial counts include (e,s)=9, (s,t)=9, (l,o)=7, (o,w)=7, and (w,e)=8. The last value is 2+6=8: the w in widest is followed by i, not e. With the stated lexical tie rule, training proceeds as follows:

The pair (s,t) tied for the first choice but disappears after (e,s) is merged; counts must therefore be updated after every selected merge. The learned rank table is:

(e,s) → 0, (es,t) → 1, (est,</w>) → 2,
(l,o) → 3, (lo,w) → 4

Encoding by merge rank

To encode a new pre-token, initialize its atomic symbols. Repeatedly merge the currently adjacent pair with the smallest rank, stopping when no adjacent pair is in the rank table. This is deterministic and does not use the training counts.

def encode_bpe(initial_symbols, rank):
    symbols = list(initial_symbols)
    while True:
        candidates = [
            (rank[(symbols[i], symbols[i + 1])], i)
            for i in range(len(symbols) - 1)
            if (symbols[i], symbols[i + 1]) in rank
        ]
        if not candidates:
            return symbols
        _, i = min(candidates)              # rank first, left position second
        symbols[i:i + 2] = [symbols[i] + symbols[i + 1]]

Encoding lowest starts as l o w e s t \lt /w\gt:

rank 0: l o w e s t </w>   → l o w es t </w>
rank 1: l o w es t </w>    → l o w est </w>
rank 2: l o w est </w>     → l o w est</w>
rank 3: l o w est</w>       → lo w est</w>
rank 4: lo w est</w>        → low est</w>

The final segmentation is {}[\text{low}, \text{est}\lt /w\gt ]. “Choose the longest vocabulary token” is not in general equivalent: BPE must respect the causal merge ranks that made a piece constructible.

Complexity and implementation data structures

  • A clear trainer that rescans all N current symbol positions for each of M merges costs O(MN) time. It is useful as a reference implementation.
  • A production trainer stores each sequence as a linked list, maps each pair to its occurrence locations, and keeps pair counts in a max-heap. A merge touches only occurrences of the winning pair and their two neighboring pairs. Heap entries can use version numbers for lazy invalidation. Worst cases remain data-dependent, but ordinary work is proportional to changed occurrences plus heap operations rather than a full corpus scan.
  • The simple encoder above is O(n^{2}) in the number of initial symbols because it rescans and splices. A linked list plus a min-heap of adjacent merge ranks gives approximately O(n \operatorname{log} n); each candidate stores neighbor/version IDs so stale heap entries are rejected.
  • Cache encoded pre-tokens only when normalization and pre-tokenization make them reusable. Bound the cache: URLs and identifiers can otherwise create unbounded cardinality.

Concrete BPE invariants: pair counts equal a slow recomputation after every test merge; merge ranks are unique; no encoder merge is applied before either child exists; decode(encode(x)) equals the documented normalized input; and identical model bytes produce identical IDs across processes.

Unigram language-model tokenization

Unigram tokenization reverses the BPE direction: begin with an overcomplete candidate vocabulary, fit piece probabilities, and prune pieces while preserving coverage. It defines a probability over every valid segmentation instead of a single merge history.

Candidate vocabulary and segmentation probability

Create seed pieces from frequent substrings (often using suffix-array statistics), required characters, reserved symbols, and optionally 256 byte-fallback pieces. For a normalized string x, let Z(x) be all segmentations whose concatenated pieces equal x. Each piece v has probability p(v), with \sum _v p(v)=1:

P(z = [v₁, ..., vₖ]) = ∏ₖ p(vᵢ) P(x) = Σ_{z ∈ Z(x)} P(z)

The independence assumption is intentionally simple; it scores segmentations, not natural-language sequences. Required atomic pieces ensure Z(x) is nonempty.

Viterbi decoding step by step

Build a lattice whose nodes are input offsets and whose edges are vocabulary pieces matching x[i:j]. The best path maximizes the sum of piece log-probabilities:

def unigram_viterbi(text, piece_logp, trie):
    n = len(text)
    score = [-inf] * (n + 1)
    back = [None] * (n + 1)
    score[0] = 0.0
    for i in range(n):
        if score[i] == -inf:
            continue
        for piece, j in trie.matches_starting_at(text, i):
            candidate = score[i] + piece_logp[piece]
            # Stable secondary rule makes equal-score paths reproducible.
            if candidate > score[j] or tied_but_preferred(piece, back[j]):
                score[j] = candidate
                back[j] = (i, piece)
    if back[n] is None:
        raise UnencodableInput
    return reverse_backtrace(back, n)

Suppose text = "abc" and p(a)=0.30, p(b)=0.20, p(c)=0.20, p(\text{ab})=0.25, p(\text{bc})=0.04, and p(\text{abc})=0.01. The four paths score:

SegmentationProductNatural log
[a,b,c]0.30\times 0.20\times 0.20 = 0.012-4.423
[ab,c]0.25\times 0.20 = 0.050-2.996
[a,bc]0.30\times 0.04 = 0.012-4.423
[abc]0.010-4.605

Viterbi returns [ab,c]. It does not simply prefer the fewest pieces: the one-piece path is worse under the fitted model.

EM-style estimation and vocabulary pruning

  1. Initialize: assign nonzero probabilities to the large seed vocabulary.
  2. E-step: for each sentence, use forward-backward on the segmentation lattice to compute each edge's posterior probability. Sum posteriors into expected count c(v).
  3. M-step: update p(v)=c(v)/\sum _u c(u) (with the implementation's smoothing/floor policy), then repeat until likelihood improvement is small.
  4. Prune: estimate the corpus-likelihood increase caused by removing each piece and resegmenting its affected occurrences. Remove a fraction of the lowest-impact pieces, never required characters, bytes, or meta-symbols.
  5. Run EM again and alternate fitting/pruning until the target vocabulary size is reached.

Forward scores use \alpha [0]=1 and \alpha [j]=\sum _{i,v=x[i:j]}\alpha [i]p(v); backward scores are analogous. Production code operates in log space with log-sum-exp. The posterior of edge (i,j,v) is \alpha [i]p(v)\beta [j]/P(x).

Concrete unigram invariants: probabilities are finite, positive for retained pieces, and sum to one within tolerance; every training and validation string has at least one lattice path; Viterbi pieces concatenate exactly to normalized input; forward and backward partition functions agree; expected piece counts sum to the expected number of pieces; and pruning cannot remove required coverage symbols.

Subword regularization and segmentation sampling

At evaluation, use the Viterbi path. During model training, sample alternative paths to reduce brittleness to one arbitrary segmentation. A common tempered distribution is

qα(z | x) = P(z)^α / Σ_{z' ∈ Z(x)} P(z')^α

Sample a complete path from the lattice with dynamic programming, or sample from an n-best list as an approximation. \alpha \to \infty approaches Viterbi; smaller positive \alpha flattens the distribution. Sampling belongs in model-data augmentation, not validation, serving, cache keys, or golden tokenizer tests.

Vocabulary-size trade-off

Let vocabulary size be V, model width d, and sequence length T.

  • Input embedding parameters: Vd.
  • Untied output projection parameters: another Vd, usually plus V biases.
  • Weight tying reuses the input embedding as the output matrix, saving approximately Vd parameters, but logits still cost roughly O(TVd) arithmetic and O(TV) materialized storage if logits are retained.
  • Full attention score work/storage scales as O(T^{2}) per layer; MLP work, residual activations, and KV-cache size scale approximately linearly with T.

Special tokens, templates, and packing

BOS, EOS, PAD, chat roles, tool delimiters, document separators, and multimodal placeholders carry model-level semantics. The tokenizer, model configuration, data formatter, and serving template must agree on their IDs and insertion rules. Adding tokens after model initialization requires resizing input embeddings and the output projection consistently, preserving weight tying, and choosing an initialization policy.

For decoder-only pretraining, documents may be packed into fixed-length sequences. BOS can mark boundaries but does not prevent cross-document attention. Strict isolation requires segment-aware or block-diagonal attention. For supervised fine-tuning, input IDs, attention masks, position IDs, and target-loss masks are distinct objects; PAD and user/system tokens are commonly excluded from target loss. See Pretraining Data, Cleaning and Mixtures for the surrounding data pipeline.

Training and evaluation workflow

  1. Freeze the contract. Specify accepted input (Unicode text or bytes), normalization, pre-tokenization, special-token policy, required coverage, decoder behavior, target vocabulary, and deterministic seed/tie rules.
  2. Sample the corpus deliberately. Sample by source, language/script, domain, time, and quality tier. Cap duplicated templates and huge sources so pair counts do not merely reproduce crawler volume. Record sampling weights and content hashes.
  3. Separate train and validation before training. Deduplicate across the boundary. Do not train tokenizer pieces on benchmark, held-out, or future model-evaluation text; that leaks surface-form statistics even without labels.
  4. Train candidate configurations. Compare algorithms, vocabulary sizes, normalization, and coverage under the same sampled bytes. Persist trainer version and every option.
  5. Evaluate slices and tails. Use prose by language, code by language, mathematics, numbers, URLs/IDs, whitespace, chat prompts, noisy Unicode, and special-token adversaries. Report means plus p50/p95/p99 and worst examples.
  6. Run model-aware measurements. Benchmark tokenization throughput, sequence-length distribution, packing efficiency, end-to-end training/inference throughput, and downstream or validation loss. A shorter tokenization is not automatically a better model interface.
  7. Version atomically with checkpoints. Store the tokenizer model/vocabulary, ordered merges or piece scores, normalizer, pre-tokenizer, template, added-token map, special IDs, code version, and an artifact hash with each model checkpoint. Refuse a mismatched hash at load time.

Metrics and normalization

For a held-out sample with B original bytes, C Unicode code points, W words under a declared word splitter, N model tokens, and total autoregressive negative log-likelihood L=-Σ log p(x_t|x_<t) in nats:

tokens per byte = N / B bytes per token = B / N tokens per word = N / W tokens per code point = N / C token perplexity = exp(L / N) bits per byte = L / (B ln 2)

Token-level perplexity is not comparable across tokenizers. Changing token boundaries changes N, the prediction events, and the vocabulary. Bits per byte normalizes the same text likelihood by original byte count and is the preferred cross-tokenizer comparison for lossless byte-recoverable models. If normalization is lossy, report that fact and use the same original-byte denominator only with care: the models are no longer assigning probability to exactly the same observable strings.

“Compression ratio” is ambiguous; always name the direction (bytes/token or tokens/byte) and whether special tokens are included. Fertility is likewise denominator-dependent, so report tokens per word, code point, and byte where relevant. Cross-link sequence length to Long-Context Modelling and vocabulary projection/cache effects to Inference.

Implementation invariants

  • Coverage: every admitted input has a valid segmentation, or the API returns an explicit error; fallback includes all 256 byte values when lossless byte coverage is promised.
  • Reversibility: decode(encode(x)) equals raw x for lossless configurations or the documented normalized form for lossy ones.
  • Determinism: training tie rules and encoding path ties are stable across process count, machine, locale, and hash seed.
  • Model alignment: IDs are in range; vocabulary rows match embedding/output rows; tied weights actually share storage after resizing and checkpoint load.
  • Special-token safety: ordinary text cannot silently become a control token; each insertion layer owns BOS/EOS exactly once; PAD never contributes to target loss.
  • Boundary semantics: packed document isolation and SFT loss masking are explicit and tested, not inferred from the presence of separator IDs.
  • Artifact identity: tokenizer and chat-template hashes are pinned to the model checkpoint and checked by training and serving.

Failure analysis

  • Train/serve drift: same vocabulary but different Unicode library, normalizer, regex, merge semantics, or added-token handling produces different IDs. Diff every pipeline stage, not only final IDs.
  • Non-reproducible BPE: equal-frequency pairs reduce in arbitrary order. Replay training with forced ties and compare the serialized merge list byte-for-byte.
  • False losslessness: an unknown token or NFKC normalization collapses inputs. Property-test round trips and keep adversarial Unicode examples.
  • Average hides exclusion: aggregate fertility improves while a small language is encoded nearly byte by byte. Rank per-slice p95/p99 and inspect the longest examples.
  • Tokenizer “win” is metric leakage: token perplexity falls solely because tokens became larger. Compare bits per byte and downstream quality on identical held-out raw bytes.
  • Template collision: untrusted content injects a role delimiter. Make special-token parsing opt-in and test serialized conversations containing literal delimiter text.
  • Packing semantic bug: separator IDs are present but attention crosses documents or labels include padding/user text. Visualize a tiny attention/loss mask and assert every allowed edge/target.

Review questions

  1. Why are BPE pair frequencies used during training but not encoding? Walk through encoding when several ranked pairs overlap.
  2. Implement a deterministic BPE trainer. Which data structures replace a full pair-count rescan, and how do you invalidate stale heap entries?
  3. Derive the unigram Viterbi recurrence and explain how forward-backward changes it from best-path decoding to EM estimation.
  4. Why can unigram select more tokens than a competing segmentation? When and how would you sample segmentations?
  5. Contrast BPE, WordPiece, SentencePiece BPE, SentencePiece unigram, byte-level BPE, and byte fallback without treating library names as objectives.
  6. For V=32k versus V=128k and d=4096, calculate tied and untied parameter deltas. Which compute terms shrink if sequence length falls 25%?
  7. Why can two models have different token perplexities but identical bits per byte? Which denominator supports tokenizer comparison?
  8. Design a fertility report that would catch regressions in Arabic, Python indentation, UUIDs, arithmetic, and emoji.
  9. How can a chat-template delimiter become an injection primitive? Where should literal user content and allowed special tokens be separated?
  10. What exact tokenizer artifacts must travel with a checkpoint, and which golden tests should gate serving?
