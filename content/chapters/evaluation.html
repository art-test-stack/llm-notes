Learning objectives

You should be able to choose metrics from the decision being made, distinguish model evaluation from system evaluation, identify contamination and judge bias, and construct a regression suite that combines capability, safety, latency, and cost.

Stage-specific evaluation

The training-method note correctly treats evaluation as stage-dependent:

Stage Useful evaluation
Pretraining held-out loss/perplexity, slice loss, downstream benchmarks, memorization, contamination checks
Continued pretraining domain benchmarks, general-capability regression, forgetting, vocabulary and long-context tests
SFT instruction following, format validity, task accuracy, tool execution, refusal calibration
Preference tuning blind pairwise comparison, reward-model agreement, length/style bias, KL drift, diversity
RL reward curves plus independent evaluation, pass@k, exploit audits, entropy/KL, stability

A reward increase is not sufficient evidence of a capability increase because the policy may exploit the reward or verifier.

Evaluation design from decisions

Start with the decision, not the benchmark. A concrete decision might be: replace the current support assistant for English and French billing conversations if task success improves without worsening safety, latency, cost, or any protected user slice. Turn that sentence into a written evaluation plan before running either model:

  1. Deployment decision: name the candidate, baseline, product surface, traffic allocation, and exact promote/hold/rollback action.
  2. Population and slices: sample from the intended production distribution, then predefine important slices such as language, domain, length, difficulty, geography, accessibility need, and new versus experienced users. Report both traffic-weighted and worst-group results.
  3. Acceptable errors: distinguish false answers, unsafe answers, false refusals, invalid formats, tool side effects, and timeouts. Set stricter tolerances for irreversible or high-severity errors.
  4. Metrics: pre-register one primary metric that decides the experiment, secondary diagnostic metrics, aggregation rules, exclusion rules, statistical tests, confidence level, and stopping rule. This prevents choosing the most favorable result after seeing the data.
  5. Baseline and minimum detectable effect (MDE): evaluate the shipped system and simple alternatives, then state the smallest change worth detecting. For example, with baseline task success of 72%, an absolute improvement below 2 percentage points may not justify migration risk; power the study for that 2-point MDE.

The unit of analysis must match the decision. If users, conversations, or documents generate several correlated examples, split and resample at that cluster level rather than pretending every row is independent.

GPT-Lab evaluation example

GPT-Lab uses two complementary evaluations:

  • Bits per byte (BPB): held-out autoregressive loss normalized by original byte count, making comparisons less dependent on tokenizer segmentation.
  • CORE: an aggregate downstream benchmark suite using multiple-choice, schema, and language-modeling tasks.

For BPB:

BPB = total negative log-likelihood in bits / total target bytes = total_nats / (ln(2) × total_bytes)

Distributed evaluation must aggregate numerator and denominator rather than averaging per-rank ratios. Ignored targets and special tokens with zero byte length must not contribute.

CORE centers accuracy against each task's random baseline:

centered_accuracy = (accuracy - random_baseline) / (1 - random_baseline)

BPB asks how well the model predicts held-out text; CORE asks whether that capability transfers to tasks. They should not be treated as interchangeable.

Statistical estimation and comparison

  • Bootstrap confidence interval: resample independent evaluation units with replacement, recompute the metric, and use the bootstrap distribution to estimate uncertainty. Resample users or conversations—not individual turns—when observations are clustered.
  • Paired bootstrap: when two models answer the same examples, resample example IDs once and carry both outputs together. Compute the candidate-minus-baseline difference on every replicate; pairing removes between-example difficulty noise.
  • Permutation test: under the null that systems are exchangeable, randomly swap their labels within each paired example and compare the observed metric difference with the resulting null distribution. This is useful when a metric's sampling distribution is unclear.
  • McNemar's test: for paired binary outcomes, test only discordant examples: baseline-wrong/candidate-right versus baseline-right/candidate-wrong. It answers whether their success probabilities differ while respecting pairing.
  • Multiple comparisons: define a small primary family, then control false positives across secondary metrics and slices with Holm–Bonferroni (family-wise error) or Benjamini–Hochberg (false discovery rate). Do not quietly test dozens of slices at unadjusted p \lt 0.05.

Effect size is not significance. Report the absolute and relative difference, its confidence interval, and a practical threshold. A tiny effect can be statistically significant at huge sample size; a useful effect can be inconclusive in an underpowered study. Choose sample size before evaluation from baseline variance/rate, MDE, significance level, desired power (commonly 80% or 90%), pairing, and expected attrition. Rare safety failures usually require far more samples or targeted stress tests than average-quality metrics.

Paired-model comparison example

Suppose baseline A and candidate B answer the same 1,000 support cases. A succeeds on 720 and B on 748, an effect of +2.8 percentage points. Of the paired cases, 61 are A-wrong/B-right and 33 are A-right/B-wrong. Run a paired bootstrap over the 1,000 case IDs to obtain a 95% confidence interval for the +2.8-point difference, a within-case permutation test for the chosen score, and McNemar's test on the 61 versus 33 binary discordances. Promote only if the pre-registered practical threshold is met and the confidence interval and corrected test support it; the raw 748 versus 720 totals alone are not sufficient.

Metric selection

  • Perplexity / loss: token prediction under one tokenizer and distribution.
  • Exact match / F1: constrained question answering or extraction.
  • pass@k: probability that at least one of k sampled solutions succeeds.
  • Pairwise preference: relative response quality under a rubric.
  • Calibration metrics: agreement between confidence and correctness.
  • Retrieval metrics: Recall@k, MRR, nDCG, metadata-filter correctness.
  • Systems metrics: TTFT, inter-token latency, end-to-end latency, tokens/s, requests/s, goodput, memory, and cost.

Goodput—the throughput that still satisfies latency SLOs—is often more informative than peak throughput.

Generative-task scoring

MethodBest useMain caution
Exact matchCanonical short answers, normalized labels, deterministic extractionRejects equivalent wording unless normalization is carefully defined
Token F1Span overlap and partially correct extractionRewards shared tokens without proving factual or semantic correctness
Semantic similarityParaphrase-tolerant screening with a validated embedding/modelCan miss negation, numbers, attribution, and domain-critical distinctions
Unit testsCode and executable tasksCoverage and hidden edge cases determine what “correct” means
Structured-output validityJSON/schema/API contracts and required fieldsSyntax validity does not imply correct field values
Human ratingsQuality dimensions requiring judgmentRequire rubrics, training, blinding, and agreement measurement
Pairwise preferencesComparing two responses when absolute scales driftRandomize order and allow ties; preferences do not reveal why
Rubric-based scoringSeparating correctness, completeness, relevance, style, and safetyAnchor every scale point with examples and report dimension scores

Automatic lexical metrics fail on open-ended generation: a factually correct paraphrase may have little word overlap, while a fluent answer can copy reference words yet reverse their meaning. Use exact or lexical scoring only where the output contract makes it valid; otherwise combine executable checks, structured validation, rubric-based human or calibrated-judge assessment, and targeted error analysis.

LLM-as-judge

LLM judges scale subjective evaluation but can prefer the first or second position, reward verbosity, favor outputs from their own model family (self-preference), follow superficial style, or be manipulated by text inside an answer. Hide system identity, randomize answer order, score swapped-order duplicates, and treat answer content as untrusted data.

Pairwise grading is usually easier and more stable for choosing between two candidates; scalar grading supports comparisons across many runs but needs anchored scale points and is prone to score drift. Allow ties. For high-impact decisions, use a diverse multi-judge ensemble, aggregate independent judgments (for example majority vote or a fitted preference model), and surface disagreement rather than assuming consensus is truth.

Judge-calibration protocol

  1. Create a frozen, stratified calibration set sized from the target agreement precision or statistical power, expected label prevalence, pairing, slice requirements, and tolerated uncertainty; there is no universal fixed minimum. Cover major slices, close calls, known failures, order-swapped pairs, verbose distractors, self-family outputs, prompt-injection attempts, and other adversarial examples.
  2. Have at least two trained human raters independently apply the same anchored rubric while blinded to model identity; adjudicate disagreements to form a gold set and record inter-rater agreement.
  3. Run the version-pinned judge with temperature, prompt, rubric, parser, and answer order recorded. Repeat with A/B order swapped.
  4. Measure agreement with adjudicated humans (pairwise accuracy and Cohen's kappa for labels; rank correlation and per-score confusion for ordinal ratings), tie behavior, and accuracy by slice. Separately measure position-flip rate and preferences for longer or self-family answers after controlling for human labels.
  5. Admit the judge only if pre-registered thresholds pass—for example, pairwise accuracy ≥85%, kappa ≥0.70, every critical slice ≥80%, and order-flip rate ≤5%. Otherwise revise the rubric/judge or route the affected cases to humans.
  6. Recalibrate on the frozen set whenever the judge model, version, prompt, rubric, decoding, or parser changes, and periodically audit a random production sample plus all judge/model disagreements.

Versioning is part of the measurement: a silent judge-model upgrade can move scores even when the evaluated system is unchanged.

Contamination and memorization

  • Track provenance and search training, tuning, retrieval, prompt, and tool corpora for exact overlap and normalized or fuzzy n-gram overlap with benchmark questions, references, and solutions.
  • Audit prompt or solution leakage through repositories, system prompts, few-shot examples, traces, public leaderboards, and retrieved documents—not only pretraining data.
  • Use temporal splits whose evaluation items postdate the training cutoff, while recognizing that an incorrect cutoff or later continued training can invalidate them.
  • Detect paraphrased contamination with semantic retrieval followed by manual review; hashing alone will miss translated, reordered, or paraphrased copies.
  • Run memorization probes such as canary extraction, completion of rare prefixes, answer-without-question tests, and comparisons of performance on suspected-overlap versus clean subsets.
  • Watch for benchmark saturation: near-ceiling scores, tiny rank changes, widespread public solutions, and poor correlation with fresh tasks mean the suite no longer discriminates. Retire, refresh, or keep a private rolling holdout.

Benchmark design

A mature suite includes:

  1. component and invariant tests;
  2. offline capability benchmarks;
  3. slices by language, domain, length, difficulty, and user group;
  4. adversarial and safety cases;
  5. end-to-end system evaluation;
  6. online outcome and monitoring metrics.

Construct it from a written task specification and sampling frame. Sample realistic inputs before looking at model failures, reserve train/development/test partitions by user or source, deduplicate within and across splits, and keep a hidden final holdout. Define inclusion rules, difficulty labels, gold-answer creation, allowed tools/context, and ambiguous-item handling. Have domain experts review a stratified sample and measure annotator agreement; discard or adjudicate items whose ground truth is not reproducible.

Pre-register the primary metric and stopping rule where possible. Report uncertainty and practical effect size, not only a point estimate. Check data lineage and benchmark contamination. Version items, labels, rubrics, prompts, templates, retrieval corpora, and decoding settings; publish change logs without exposing the hidden solutions. Refresh with newly sampled production cases and retire saturated or leaked items while preserving an anchored subset for longitudinal comparison.

Slice and robustness evaluation

Report language, domain, input/output length, difficulty, and demographic or user-group slices with sample counts and confidence intervals. Slice definitions should follow likely harms and deployment needs, not be invented after an aggregate result disappoints. For small groups, collect more data or use uncertainty-aware estimates rather than hiding them.

Test robustness with meaning-preserving prompt perturbations (format, spelling, casing, distractors, instruction order), controlled difficulty changes, and realistic distribution shifts across time, geography, sources, products, and user behavior. Track consistency under perturbation and worst-group performance alongside the population-weighted mean. A candidate that gains two points overall but loses ten points for a critical language or user group should fail the gate.

Holistic system evaluation

Evaluate the deployed pipeline, not just the base model. Replay representative end-to-end traces and retain component outputs so a failure can be localized:

  • Retrieval: Recall@k/nDCG, citation support, freshness, authorization filters, and answer quality conditional on retrieved evidence.
  • Tools: selection, argument/schema validity, execution success, side-effect correctness, recovery from tool errors, and unnecessary-call rate.
  • Latency and cost: end-to-end and component p50/p95/p99, time to first token, output length, accelerator time, external calls, and cost per successful task—not merely per request.
  • Goodput and reliability: useful requests completed inside the latency SLO, timeout/error rates, availability, retry amplification, and degradation behavior under load.
  • Security: prompt injection, data exfiltration, cross-tenant access, unsafe tool actions, secret exposure, and abuse resistance.
  • Calibration: confidence, abstention, escalation, and citation behavior aligned with correctness and risk.
  • Trace evaluation: score the final outcome plus retrieval, reasoning/action trajectory, tool observations, policy decisions, and failure recovery. A correct final answer reached through an unsafe action is still a system failure.

Systems scaling

Strong scaling keeps the total problem fixed while adding devices; communication eventually dominates. Weak scaling grows the problem with device count and is easier to make look efficient. State clearly which one is measured.

Failure modes

  • one aggregate score hiding severe slice regressions;
  • benchmark contamination;
  • changing prompts between model comparisons;
  • averaging ratios incorrectly across ranks;
  • reward or judge exploitation;
  • reporting only mean latency and omitting p95/p99;
  • using the same model as generator and uncalibrated judge;
  • treating statistical significance as practical value.

Regression and release gates

Keep a versioned regression suite of immutable golden tests, sampled production traces, fresh capability tasks, adversarial safety cases, and slice-specific failures. Define rollback before launch: immediately roll back on any critical safety/security event, cross-tenant leak, or unauthorized side effect; roll back if p95 latency exceeds 2.5 s or request errors exceed 1% for 10 consecutive minutes, or if a sequentially monitored primary outcome drops by more than 2 points with the pre-specified alert confidence. Keep the previous artifact and configuration deployable; canarying is not a rollback plan unless rollback is fast and tested.
