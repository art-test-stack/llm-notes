Learning objectives

By the end of this chapter, you should be able to define an agent precisely, explain the orchestration loop and state transitions, identify operational and safety failure modes, and design an evaluation that scores the complete trajectory rather than only the final text.

Technical framing

The timeline note distinguishes ordinary code completion from agentic software engineering: an agent must understand repository state, select tools, execute actions, and react to observations. The screening note also raises the practical question of how LLM and agent teams combine models with domain workflows. GPT-Lab provides an adjacent orchestration example: the trainer coordinates model, optimizer, dataloaders, schedules, logging, evaluation, and checkpointing without being the Transformer itself.

That separation is a useful mental model. The model proposes; the orchestration layer owns state, permissions, execution, recovery, and termination.

Detailed treatment

An agent is a repeated decision loop:

state → model/policy → proposed action → validation → execution → observation → updated state

The model proposes; the orchestrator validates actions against tool schemas, permissions, current state, and budgets before execution. It then records the observation and decides whether to continue, stop, recover, or ask a human. Reasoning techniques may improve a proposal, but they do not replace deterministic orchestration controls.

An agent is unnecessary when a deterministic function, database query, search endpoint, fixed workflow, or one-shot model call already solves the task. Extra loops add latency, cost, nondeterminism, and failure surface. Prefer a conventional program when the steps and rules are known; reserve model decisions for genuine ambiguity.

State model

Separate the append-only record of what happened from the mutable projection used to make the next decision. The event log is authoritative; current working state is a reconstructible cache.

AgentState {
  run_id, tenant_id, goal, status, state_version
  event_log[]             // immutable, ordered proposals, decisions, executions, observations
  working_state           // current files, facts, plan position, hypotheses
  tool_observations[]     // value, source, captured_at, freshness, trust label
  pending_actions[]       // action_id, tool, arguments hash, risk, idempotency key
  budgets { steps_left, tokens_left, tool_cost_left, deadline }
  approvals[]             // scope, approver, decision, expiry, consumed_by
  checkpoints[]           // event offset, state snapshot hash, external-effect receipts
  termination { goal_tests[], cycle_window, repeated_action_limit }
}

Every proposed action receives a stable action ID and is appended before execution. Its observation includes timestamps, tool version, exit status, and any external side-effect receipt. Approvals are scoped to a specific action or narrow capability and expire; they are not a global Boolean.

After process failure, load the latest valid checkpoint, replay later events to rebuild working state, and reconcile every pending action against its idempotency key or external receipt. Never assume that an absent observation means the action did not happen.

Planning strategies

  • Explicit plans expose intended steps, dependencies, success checks, and approval points. They are useful for auditability, not a promise that reality will cooperate.
  • Incremental planning chooses only the next safe step from fresh evidence. It handles uncertainty well but needs strong termination controls.
  • Hierarchical decomposition divides a goal into bounded subgoals, then into executable actions. Each child needs its own input, output, budget, and completion test.
  • Reflection asks the acting model to inspect its recent result and revise. It is cheap, but correlated with the original mistake.
  • Critic loops use a separate role, prompt, model, or deterministic checker to challenge an action or result. A critic advises; the orchestrator still decides.
  • Search explores several candidate plans or actions and scores them. Beam search, best-first search, or tree search can improve hard decisions at rapidly increasing inference and tool cost.

Plans drift when observations invalidate assumptions but the agent continues following old steps. Replanning after every small surprise creates the opposite failure: useful work is discarded and the agent never commits. Replan only on a material invariant violation, failed goal test, blocked dependency, or changed risk; cap revisions and retain the reason for each change.

Memory models

MemoryContentsLifetime and control
Conversation stateCurrent messages, tool results, and summarized contextPer run; compact carefully so constraints and unresolved decisions survive
Episodic memoryPrior trajectories: what happened in a particular taskRetrieve similar episodes with provenance, outcome, and timestamp
Semantic or vector memoryFacts and documents indexed by meaningUse RAG with access filters, freshness checks, citations, and reranking
Procedural memorySkills, policies, playbooks, and tool instructionsVersioned and reviewed; higher trust than retrieved content, but never immutable policy by accident

Retrieval should combine relevance with tenant, authorization, freshness, source trust, and task scope. Forget duplicate, expired, disproven, low-value, or retention-limited entries; keep tombstones or audit records when deletion itself matters. More memory is not automatically better: stale facts anchor decisions, and poisoned memory can persist malicious instructions across runs. Treat retrieved text as data, not authority, and enforce strict tenant separation in storage, indexes, caches, embeddings, logs, and evaluation datasets.

Termination and budgets

A bounded agent checks termination before and after every action. It stops successfully only when explicit goal tests pass—for example, the requested diff is present, targeted tests pass, and no unauthorized files changed. It stops unsuccessfully when any hard budget is exhausted: step limit, token limit, cumulative tool-cost limit, or wall-clock deadline.

Cycle detection computes a normalized signature from the control state, relevant working-state hash, action type, canonicalized arguments, and observation class. If the same signature appears more than a configured number of times inside a rolling window without measurable progress toward a goal test, the run is cycling. Repeated-action detection is the narrower rule: reject or escalate an identical side-effecting action with the same target and arguments unless the previous attempt is proven not to have executed.

Progress must be observable, such as a newly satisfied goal predicate or reduced set of unresolved failures—not a new paraphrase of the plan. On cycles, ambiguous side effects, missing authority, irreducible uncertainty, or budgets nearing a destructive cutoff, preserve state and escalate to a human with the goal, evidence, attempted actions, receipts, remaining choices, and recommended next step.

Recovery and failure semantics

FailureRequired response
Tool timeoutMark outcome unknown, query status using the action ID, then retry only if non-execution is proven or the operation is idempotent
Partial side effectReconcile receipts and actual external state; complete safely, run a compensating action, or request manual intervention
Stale observationCheck version, ETag, timestamp, or source revision before acting; refresh and invalidate dependent plan steps
Process crashRestore a checkpoint, replay the immutable log, rebuild projections, and resolve pending actions before continuing
Retryable failureUse bounded exponential backoff with jitter and a retry budget; do not retry invalid arguments or denied permissions
Irreversible or ambiguous failureStop mutation, preserve evidence, and escalate with a concrete manual recovery procedure

Idempotent replay means repeating an event or action produces the same externally visible result, normally through idempotency keys, compare-and-swap preconditions, deduplication, or upserts. When undo is impossible, a compensating action restores the business invariant rather than pretending history did not occur. Compensation is itself logged, authorized, and fallible.

Multi-agent systems

Role decomposition can assign planning, research, execution, and criticism to separate agents, or partition work by independent subsystem. Shared state makes discoveries visible but increases contention, accidental coupling, and data exposure. Private state improves isolation and specialization but requires explicit, lossy communication. A practical design keeps an authoritative shared task ledger while agents retain private scratch context.

Coordination consumes tokens and time: agents must delegate, serialize findings, resolve conflicts, and merge outputs. Common failures include ambiguous ownership, circular delegation, incompatible assumptions, message loss, stale shared state, conflicting writes, premature consensus, redundant searches, and several agents repeating the same work. Use unique task IDs, owners, dependency edges, leases, versioned artifacts, and a single merge authority.

Multiple agents do not automatically improve quality. They may share the same model bias, amplify a false premise, dilute accountability, or spend the budget on communication. Add an agent only when work is genuinely parallel, roles need different permissions or context, independent evidence reduces correlated error, or the coordination cost is lower than the expected gain. Compare against a single-agent baseline at the same total budget.

Trajectory-level evaluation

Evaluate both outcome and process. A polished final answer can hide fabricated evidence, unsafe calls, unrecovered side effects, or excessive exploration. See also evaluation and benchmark design and agent security.

Test with normal tasks and adversarial scenarios: tool timeouts, duplicate events, stale reads, corrupted memory, injected instructions in retrieved content, revoked approval, crash after side effect but before acknowledgment, and conflicting agent writes. Report distributions and worst cases, not only mean success. Re-run identical fixtures and compare both final outputs and normalized trajectories.

Failure modes and safety controls

  • infinite or oscillating loops;
  • stale memory overriding current evidence;
  • cascading dependency failures;
  • indirect prompt injection through retrieved documents or tool output;
  • repeated side effects after retries;
  • over-broad credentials;
  • missing termination conditions;
  • state that cannot be replayed after a failure.

Apply least-privilege credentials, tool allowlists, schema validation, sandboxing, output encoding, network and path restrictions, scoped approvals, secret redaction, immutable audit logs, and separation between untrusted observations and system policy. High-impact actions need deterministic preconditions and, where appropriate, human approval. Security decisions live outside the model so a prompt cannot negotiate them away.
