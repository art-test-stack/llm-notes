Learning objectives

You should be able to derive exact speculative sampling, trace block verification and KV-cache rollback, estimate the break-even point from measured costs and acceptance, compare proposal mechanisms, and explain how speculation changes a continuously batched serving system.

Core idea

A cheaper draft mechanism proposes several future tokens. The target model evaluates those positions in one parallel verification pass. An acceptance rule keeps a valid prefix of draft tokens and samples a correction when needed.

current prefix → draft proposes y₁…y_k
→ target scores all proposals in parallel
→ accept valid prefix → sample correction if required → repeat

With the correct rejection-sampling rule, speculative decoding preserves the target model's output distribution; it is not an approximate model-quality shortcut.

Exact speculative sampling

Fix the current accepted prefix x. Let q(t | x) be the draft distribution and p(t | x) the target distribution over the next token after applying the intended sampling transforms. The draft samples a proposal y ~ q. Draw u ~ Uniform(0,1) and accept y when:

u ≤ a(y), where a(y) = min(1, p(y | x) / q(y | x)).

The ratio is needed only for a sampled token, so q(y \mid x) \gt 0. If the proposal is rejected, do not emit it. Instead sample a correction token from the residual distribution:

r(t | x) = max(0, p(t | x) - q(t | x)) / Z Z = Σ_v max(0, p(v | x) - q(v | x)).

If Z = 0, then p = q and rejection has probability zero, so the correction branch is unreachable. Target mass on tokens where q=0 is included in the residual.

Why the output distribution is p

The probability that token t is proposed and accepted is

q(t) min(1, p(t)/q(t)) = min(q(t), p(t)).

The total rejection probability is

β = 1 - Σ_v min(p(v), q(v)) = Σ_v max(0, p(v) - q(v)) = Z.

Therefore the probability that the algorithm emits t, either by acceptance or correction, is

P(output=t) = min(p(t), q(t)) + β r(t) = min(p(t), q(t)) + max(0, p(t)-q(t)) = p(t).

This proves the one-step result. Reapplying it at every realized prefix gives the same conditional distribution as ordinary target sampling at every position, hence the same joint sequence distribution. The proof assumes probabilities and random draws are implemented consistently; finite-precision and non-deterministic kernels can still cause small empirical differences.

Block verification

  1. Draft: sample y₁…y_k serially, recording each conditional proposal distribution q_i(· | x,y₁…y_{i-1}).
  2. Score in parallel: run the target once over the proposed block. Causal masking produces all target distributions p_i(· | x,y₁…y_{i-1}) in one wider pass.
  3. Verify in order: apply min(1,p_i(y_i)/q_i(y_i)) from left to right. If j is the first rejected position, the accepted prefix length is a=j-1.
  4. On rejection: keep y₁…y_a, discard y_j…y_k, and sample one token from r_j ∝ max(0,p_j-q_j). Later proposals cannot be reused because their distributions were conditioned on the rejected token.
  5. On full acceptance: keep all k proposals and sample a bonus token from the target's next-position distribution produced by the verification pass. A successful block can therefore advance by k+1 output tokens.

Verification is computationally parallel but acceptance is logically sequential: the target probability at position i is valid only while all earlier proposals remain on the realized prefix.

Cache commit and rollback

Treat speculative cache updates as a transaction. Target verification temporarily writes K/V for the proposed positions. After accepting a proposals, commit only the cache entries for the accepted prefix and roll the logical target-cache length back over rejected and unused entries. Whole paged-cache blocks beyond the committed length can be released; a partial tail block resets its write offset. Stale bytes may remain physically but must be unreachable and overwritten before reuse.

The correction or bonus token has been sampled but normally has not yet had its own K/V computed; it is processed at the next model call. The draft cache must also discard proposal state after the accepted prefix and then consume the target-chosen correction or bonus token before drafting again. Roll back token buffers, positions, stop state, grammar state, and any counter-based RNG bookkeeping together with K/V. See cache layouts and lifecycle for contiguous and paged-cache mechanics.

Sampling-parameter consistency

Define p as the target distribution the user actually requested: after temperature, penalties, top-k/top-p or min-p filters, bad-word masks, grammar constraints, and other logit processors in their specified order. Define q from the distribution the draft actually sampled, not from unprocessed draft logits. The draft and target need not have equal logits, but both sides must use the same accepted prefix and synchronized stateful processors. Applying different user sampling policies accidentally, or computing the ratio from probabilities produced before filtering, breaks the claimed algorithm. A narrower draft support is mathematically allowed because the residual restores missing target mass, but it may lower acceptance.

Expected performance

Let k be proposal length, C_d(k) the cost of producing the draft block, C_v(k) the target verification cost, C_{o} bookkeeping/communication cost, and C_t(1) the baseline cost of one target decode step. Under the simplifying assumption that every proposal is accepted independently with probability α, the expected number of accepted draft tokens per verification is:

E[A] = Σ(i=1…k) P(first i proposals are accepted)
     = Σ(i=1…k) α^i
     = α(1-α^k)/(1-α),  for α ≠ 1; and E[A]=k for α=1.

Every cycle also emits one correction after a rejection or one bonus target token after full acceptance, so E[N] = E[A] + 1 output tokens. The approximate latency speedup and break-even condition are:

speedup ≈ (E[A] + 1) C_t(1) / (C_d(k) + C_v(k) + C_o) break even when C_d(k) + C_v(k) + C_o < (E[A] + 1) C_t(1).

This is a first-order model, not a promise: acceptance events are prefix- and position-dependent, verification cost is shape-dependent, and batching, cache traffic, synchronization, and draft placement affect the measured terms.

Worked numerical example

Take k=4, per-position acceptance \alpha =0.8, draft cost C_{d}=0.4 C_{t}(1), four-token target verification cost C_{v}=1.2 C_{t}(1), and overhead C_{o}=0.1 C_{t}(1).

E[A] = 0.8 + 0.8² + 0.8³ + 0.8⁴ = 2.3616 E[N] = 3.3616 output tokens cycle cost = 0.4 + 1.2 + 0.1 = 1.7 baseline target steps speedup ≈ 3.3616 / 1.7 = 1.98×

The cycle beats the 3.3616 C_t(1) baseline cost. If placement or batching raised the cycle cost above that value, the same acceptance rate would no longer break even. This is why draft accuracy alone is not a speed metric.

Where speedup comes from

Autoregressive decode normally requires one target-model pass per token. Verification turns several serial target calls into one wider call that can use the GPU more efficiently. Speedup depends on:

  • draft cost;
  • acceptance rate;
  • proposal length;
  • target verification efficiency;
  • batch size and scheduler behavior;
  • cache updates and rollback cost;
  • hardware utilization.

A draft that is cheap but inaccurate may reduce speed. A strong draft may be too expensive. Longer proposal blocks are not always better because rejection wastes later candidates.

Serving interactions

  • Continuous batching: a scheduler iteration no longer advances every decode request by exactly one token. A completed verification normally commits one through k+1 tokens, may finish mid-block, and may roll back temporary cache entries.
  • Unequal progress: high-acceptance requests release capacity and reach stop conditions faster while low-acceptance requests consume more verification cycles. Token budgets and completion estimates must use committed tokens, not proposed positions.
  • Variable block sizes: choose k from recent acceptance, remaining maximum length, available KV blocks, batch shape, and latency target. Large blocks favor high acceptance; short blocks limit wasted target work and tail latency.
  • Fairness: charging one scheduling turn per verification can favor requests that accept many tokens; charging only committed tokens can let repeated low-acceptance verification consume excess compute. Fair queues should account for measured draft plus verification work while enforcing wait-time or TPOT bounds.
  • Draft/target placement: colocating them avoids communication but duplicates active weights and caches on scarce accelerator memory. Separate GPUs can overlap draft and target work, but transfer latency, topology, pipeline bubbles, and backpressure enter the break-even equation.
  • Memory duplication: an independent draft usually has its own weights and KV cache, while target verification needs temporary slots for all proposals. Capacity planning must include both caches, speculative tail blocks, tree candidates, and rollback fragmentation.

Continuous batching can improve target utilization but may reduce the marginal gain from making each request wider. Benchmark the actual scheduler, concurrency, and SLO policy; see static versus continuous batching and scheduling policies.

Tokenizer and vocabulary compatibility

  • Shared tokenizer: the simplest exact path uses identical token IDs, normalization, special tokens, and chat templates. Target probabilities and proposal probabilities then refer to the same events.
  • Vocabulary mapping: different tokenizers require mapping draft continuations into target-token sequences and defining a valid proposal probability over those sequences. A text-level retokenization alone does not provide the per-target-token q needed by the acceptance ratio, and boundaries may change with surrounding text.
  • Sampling filters: temperature, top-k, top-p, min-p, and truncation must be reflected in the normalized p and q used by verification. Compute probabilities after masking and renormalization.
  • Logit processors: repetition/frequency penalties, forced tokens, bad-word lists, minimum length, and stop rules are prefix-stateful. Advance their state only for committed tokens and roll it back with rejected proposals.
  • Constrained decoding: grammar or schema state is part of the prefix. Apply the allowed-token mask before forming both distributions. A draft proposal forbidden by the target has p(y)=0 and is rejected; branch or n-gram proposals must not move the committed automaton state until accepted.

Without a sound vocabulary-level probability mapping, a mismatched-tokenizer draft can still be used as a heuristic candidate generator for a separately designed verifier, but the simple p(y)/q(y) proof above does not apply automatically.

Evaluation

Also record draft cost, target verification latency by block/batch shape, TTFT, cache memory, rollback rate, energy or accelerator-seconds, and baseline results under identical target sampling parameters. Sweep proposal length and concurrency rather than tuning on one workload.

Distribution-equivalence test design

  1. Use a tiny known p and q to exhaustively check that acceptance plus residual correction produces p, including q(t)=0 and p(t)=0 cases.
  2. Compare speculative and ordinary target sampling over many trials at the first token and over short sequences. Test greedy separately; it is not evidence for sampling correctness.
  3. Repeat with temperature, truncation, penalties, EOS, constrained decoding, partial rejection, full acceptance, and paged-cache block boundaries.
  4. After every rejection, compare subsequent target logits and logical cache lengths with a clean non-speculative replay of the committed tokens.

Failure modes

  • acceptance implementation changes the target distribution;
  • cache state includes rejected tokens;
  • draft/target tokenizer mismatch;
  • poor acceptance under domain shift;
  • synchronization overhead dominates small batches;
  • benchmarking a different sampling distribution;
  • proposal length tuned only on one workload.

Review questions

  1. Derive min(1,p(y)/q(y)), the residual [p-q]₊, and the final equality to p.
  2. For a rejection at proposal three, state which tokens and target/draft cache entries commit.
  3. Derive expected accepted tokens for k proposals with constant acceptance α, then write the break-even inequality.
  4. Explain why high draft accuracy alone does not guarantee speedup.
  5. Compare independent drafting, early exit, Medusa-style heads, and prompt lookup for memory, training, and workload sensitivity.
  6. Explain how continuous batching and fairness accounting change when requests advance by different token counts.
