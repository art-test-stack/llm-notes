Learning objectives

You should be able to design a synthetic-data pipeline, distinguish generation from validation, explain rejection sampling and distillation, reason about mixture ratios and provenance, and identify model-collapse, contamination, and self-judging risks.

Why synthetic data is used

Synthetic data can expand scarce labels, target rare cases, create curricula, expose a student to a teacher's behavior, generate tool traces, and scale tasks with programmatic verification. In scientific and engineering settings, simulators can generate labelled states or fields under controlled parameters.

Synthetic data is not automatically high quality. Its value depends on the generator, sampling diversity, validation, deduplication, and how it is mixed with real data.

These sources are complementary rather than interchangeable: demonstrations transfer behavior, preference pairs shape rankings, verifiable problems train checkable skills, adversarial examples target weaknesses, and simulations cover controlled physical regimes. The source choice should follow the capability and available ground truth.

Pipeline

task/source selection → prompt or simulator generation → candidate generation
→ validation/filtering → deduplication → difficulty/diversity balancing
→ provenance labelling → mixture with real data → independent evaluation

Task generation

  1. Start from seed tasks: use a small, reviewed set that spans the intended skills and domains rather than one large undifferentiated prompt pool.
  2. Mutate prompts: change entities, formats, perspectives, tools, or required operations. Measure semantic distance so mutation does not become trivial paraphrase duplication.
  3. Control difficulty: vary reasoning depth, distractors, context length, tool count, numerical precision, or compositional steps. Confirm difficulty using solve rates, not generator claims alone.
  4. Generate constraints: sample compatible requirements such as output schema, forbidden operations, latency budget, proof form, or API limits; reject internally inconsistent combinations.
  5. Track domain coverage: define a domain-by-skill matrix, target underrepresented cells, and cap overrepresented cells instead of trusting uniform prompt sampling.
  6. Vary templates: use multiple independently written templates and free-form generation; normalize and cluster instructions to detect template-shaped duplicates.

Deduplicate at three levels: exact normalized text, near-duplicate embeddings or shingles, and task semantics. Keep a mutation only if it changes a meaningful variable, constraint, solution path, or covered concept.

Candidate generation

For each task, define a candidate distribution q(y | x). Temperature flattens or sharpens token probabilities; top-p truncates sampling to a cumulative probability mass. Neither is a universal diversity knob: inspect actual answer and strategy diversity.

  • Multiple candidates: sample k responses per task so filtering can compare outcomes rather than approve a single draw.
  • Teacher ensembles: mix teachers from different model families or specializations to reduce a single teacher's blind spots.
  • Diverse decoding: vary temperature, top-p, prompts, system roles, and random seeds; use diversity penalties only when they improve semantic rather than cosmetic variation.
  • Search: use beam search, best-of-N, tree search, self-consistency, or tool-assisted exploration when a verifier can cheaply score intermediate or final states.
  • Cost versus diversity: increase k until the marginal accepted novel candidate per generation token no longer justifies its cost. More samples from one narrow teacher may add less diversity than fewer samples across independent teachers.

Validation and filtering

Use the strongest available ground truth first, then learned or human judgement for properties that cannot be checked exactly. Combine filters as a documented decision rule; do not treat fluency or generator confidence as correctness.

Verifier error-analysis protocol

  1. Before large-scale generation, draw a stratified audit sample across source, domain, difficulty, generator, score band, and both accepted and rejected outcomes.
  2. Have qualified humans or a stronger exact process assign ground-truth accept/reject labels while blinded to the filter decision. Double-label ambiguous cases and adjudicate disagreements.
  3. Build a confusion matrix. Estimate false-positive rate FP / (FP + TN) and false-negative rate FN / (FN + TP), with confidence intervals, overall and per stratum.
  4. Inspect false positives for loopholes, factual errors, unsafe content, and shared generator-judge bias; inspect false negatives for equivalent answers, uncommon valid strategies, and over-strict formatting.
  5. Choose thresholds from the cost of each error. High-risk demonstrations may require low false-positive rates; diversity mining may tolerate more manual review to reduce false negatives.
  6. Freeze a verifier test set, version every rule/model, and repeat the audit after generator, domain, prompt, or threshold changes. Route uncertain score bands to human review.

Cross-model agreement should be evaluated like any other filter. Agreement between closely related models is not independent evidence; report performance by judge family and on adversarial disagreements.

End-to-end example: generating code-repair demonstrations

  1. Task generation: begin with 500 reviewed Python functions and unit tests. Mutate boundary conditions, data types, and one bug operator; reject mutations that do not make at least one test fail. Cluster task statements and keep at most one trivial paraphrase per cluster.
  2. Candidate generation: sample eight repairs per failing task: four at temperature 0.3/top-p 0.9 and four at temperature 0.8/top-p 0.95, split across two unrelated teachers. Give both teachers the same sandbox tools but not hidden tests.
  3. Exact filtering: parse and compile each patch, run public and hidden tests in a sandbox, apply time and network limits, and reject patches that alter tests or unrelated files.
  4. Quality filtering: reject duplicate patches, require a minimal-diff bound, scan for hard-coded test outputs, and manually review a stratified sample including near-threshold failures.
  5. Retention: retain up to two semantically different passing repairs per task, weighted by test coverage and strategy rarity rather than keeping only the judge's top-ranked prose.
  6. Audit and provenance: record seed task, mutation, teacher/version, prompt, random seed, sampling settings, sandbox and test-suite versions, result, and acceptance reason. Estimate verifier false positives with extra hidden tests and human code review.
  7. Training and evaluation: mix accepted repairs with real code-review data, then evaluate on a deduplicated real-repository benchmark created before this generation run.

This example separates task validity, response correctness, quality selection, and downstream evaluation. Passing generated tests is necessary but not sufficient evidence that a repair generalizes.

Rejection sampling

Sample candidates y ~ q(y | x) from an explicit candidate distribution, score them with verifier v(x, y), and retain candidates above an acceptance threshold τ. Fine-tuning on the retained set converts inference-time exploration into supervised data, but the retained distribution is conditioned on the verifier.

  • Threshold: calibrate τ on labelled data and separately by domain when score meanings differ.
  • Top-1 retention: keeping the highest-scored response is simple but discards valid alternative strategies and is sensitive to score noise.
  • Weighted retention: keep several passing candidates with weights based on correctness, quality, and rarity; cap candidates per task so easy prompts do not dominate.
  • Selection bias: the dataset overrepresents what the current generator can produce and the verifier can recognize, not necessarily what users need.
  • Diversity collapse: strict best-of-N can converge on one style or strategy. Monitor semantic clusters, n-gram/template concentration, and strategy coverage before and after filtering.
  • Iterative regeneration: regenerate failed or undercovered cells with revised prompts or a different teacher, but limit retries and retain failure metadata so repeated easy successes do not hide hard regions.

Distillation

Distillation trains a student on teacher logits, responses, rationales, or task labels. It can compress a larger model or transfer a specialized behavior. The student may inherit teacher mistakes and may learn stylistic imitation without the same underlying capability.

Synthetic preference data

Construct a chosen/rejected pair only after both responses pass basic validity checks. The label should express a relevant quality difference, not merely that one response is broken. Require a calibrated score margin for automatic labels; route near-ties to human review, retain them with soft labels if the training method supports uncertainty, or omit them.

  • Chosen/rejected construction: sample multiple responses to the same prompt, randomize their presentation, score against a fixed rubric, and preserve the pair's source and score rationale.
  • Teacher bias: a teacher may prefer its own phrasing and reasoning conventions. Use independent judges and human audits, including pairs where the teacher did not generate either answer.
  • Position and verbosity bias: swap left/right order, normalize formatting where appropriate, and test matched pairs where answer length changes without content quality changing.
  • On-policy candidates: responses from the policy being optimized expose its current errors and decision boundary but must be refreshed as the policy changes.
  • Off-policy candidates: responses from teachers, earlier checkpoints, or other systems broaden quality and style but may be too easy or unlike the deployed policy distribution.

Mix on-policy and off-policy pairs, stratify by score margin, and report results separately. See post-training for how pair construction interacts with preference-optimization objectives.

Verifiable reasoning data

Mathematics, code, formal reasoning, and simulations can provide programmatic rewards and support search. Generated tasks and solutions should be checked for leakage, malformed tests, trivial shortcuts, and verifier exploits. A model should not generate both the data and the only uncalibrated judgement of that data. See reasoning training and RLVR for using outcome and process signals.

Mixture design

Choose real-versus-synthetic proportions at the token or example level and state which one. Source weighting controls the probability of drawing from a source; quality weighting controls the contribution of an example after it is drawn. Both affect effective repeated exposure: a small, high-weight synthetic set may be seen far more often than a larger nominal proportion suggests.

  • Curriculum schedules: use synthetic data early for basic or verifiable skills, later for targeted hard cases, or decay it as the model approaches deployment distribution. Compare schedules rather than assuming easy-to-hard is best.
  • Coverage constraints: set floors for important real domains and caps for any generator, template, or teacher family.
  • Quality weighting: calibrate weights from audited verifier precision; avoid turning an uncalibrated reward score directly into a large training multiplier.
  • Exposure accounting: report expected epochs or token reuse per source, including oversampling and curriculum phases.

Model collapse and feedback loops

Model collapse is a possible feedback-loop failure, not an inevitable result of using synthetic data. It describes degradation when successive training distributions narrow around earlier models' outputs: rare modes and tail behavior disappear, systematic errors gain frequency, and the next generator has less real variation from which to recover.

  • Distribution narrowing: track semantic-cluster entropy, vocabulary and format diversity, strategy diversity, and coverage of the real reference distribution before and after filtering.
  • Error amplification: maintain a stable human-labelled error suite and trace whether each error class grows across successive synthetic generations.
  • Tail loss: report performance and inclusion rates by rare domain, language, difficulty, demographic slice, and low-density region rather than only global averages.
  • Generator-judge coupling: shared blind spots let plausible errors pass. Cross-family judges, exact checks, and human audits reduce but do not eliminate this dependence.
  • Related teacher/student families: close architectures, training data, and post-training recipes can make apparent cross-model agreement highly correlated.
  • Successive generations: label generation number, preserve real-data anchors, compare each generation to the original real distribution, and stop or rebalance when diversity or tail metrics regress.

Collapse risk can be controlled by supplementing rather than replacing high-quality real data, preserving provenance, injecting independent sources, auditing filters, and selecting for diversity as well as score. The relevant claim is empirical: test whether a particular pipeline narrows or degrades under repeated generations.

Simulator-generated engineering data

A simulator defines a synthetic world, so the data specification must define where that world is trustworthy.

  • Parameter ranges: sample physically meaningful ranges and dependencies; include rare but valid regions rather than independent uniform draws by default.
  • Boundary and initial conditions: enumerate types, units, compatibility constraints, and how frequently each regime appears.
  • Solver tolerances: store convergence criteria, residuals, timeouts, failed solves, and sensitivity to tighter tolerances.
  • Mesh and discretization: record grid, element type, resolution, time step, and convergence studies; avoid teaching mesh artefacts as physics.
  • Domain randomization: randomize geometry, materials, loads, sensors, and nuisance parameters within defensible priors to improve robustness.
  • Simulation-to-reality gap: compare against experimental or field measurements, model discrepancy explicitly, and reserve real observations for independent validation.
  • Out-of-distribution physical regimes: create held-out extrapolation splits beyond training combinations, but do not claim validity beyond the solver's governing assumptions or stability region.

A surrogate inherits the simulator's equations, approximations, numerical errors, and sampled support. Solver success is not evidence of real-world accuracy.

Provenance and contamination

For every example, record the generator and version, complete prompt/template, source seed task and random seed, temperature/top-p and other sampling settings, verifier and version, raw scores, acceptance reason, timestamp, human edits, and generation number. Simulator records also need solver configuration, parameters, mesh, tolerances, and diagnostics.

  • Benchmark overlap: hash and semantically match seed tasks, prompts, retrieved context, generated tasks, and outputs against evaluation sets. Quarantine uncertain overlaps before training.
  • Deletion: maintain stable example and lineage identifiers so a contaminated source, generator run, or derived descendant can be removed and affected checkpoints identified.
  • Reproducibility: preserve prompts, seeds, versions, environments, and decision logs. Exact regeneration may still be impossible for nondeterministic hosted models, so archive raw generations and verifier outputs.

Failure modes

  • generator and judge share the same blind spots;
  • high-confidence fluent errors pass filtering;
  • duplicated templates dominate the set;
  • benchmark questions appear in prompts or generated outputs;
  • verifier loopholes produce reward hacking;
  • synthetic style crowds out natural variation;
  • difficult examples are filtered away;
  • simulator coverage is mistaken for physical universality;
  • evaluation uses synthetic data from the same generator.
